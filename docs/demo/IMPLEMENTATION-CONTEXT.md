## 1. Source Gateway 간헐 503 — `60d8a2d`

**원인:** EKS의 Gateway Envoy가 다른 노드의 앱 Pod로 연결할 때 출발 주소가 VPC가 모르는 Cilium 내부 주소였습니다. VPC가 Cilium 밖에서 패킷을 버려 Hubble에는 드롭이 보이지 않았습니다. 같은 노드에서는 정상이어서 노드를 2대로 늘린 뒤 드러났습니다.

**수정:** Cilium 설정 세 줄로 해당 내부 대역의 출발 주소만 노드 IP로 변환했습니다. Pod는 원래 VPC 주소를 유지합니다. `aws-cni` chaining을 사용하는 출발지 EKS에 해당하며 온프렘·GKE에 같은 수정을 적용하지 않습니다.

| 확인 | 결과 |
|---|---|
| 연속 요청 | 600/600 HTTP 200 |
| 쓰기 50 + 읽기 150/s, 60초 | 12,000건 성공 |
| 노드 간 연결 실패 | 0 |
| 운영자 추가 요청 | 100/100 HTTP 200 |

후속 [SHIFT 왕복 기록](../evidence/shift/lb-roundtrip-after-gw-fix-20261103T044632/README.md)에서도 앱에 도달하지 못한 오류(`X-Served-By` 없는 응답)가 없었습니다.

## 2. S2 두 역할 동시 실행 — `e6cf13f`

| 구간 | 이전 | 개선 뒤 |
|---|---:|---:|
| 버킷 정책 | 227초 | 150–210초 |
| Secrets Manager → OpenBao 코드 수정 | 315초 | 180–187초 |
| 제안서 확정 → 판정 | 118–152초 | 27–54초 |

시간 개선은 Pod 삭제 대기 30초를 1초로 줄이고, 제안서가 고정되는 즉시 검증 Job을 시작해 정적 검증과 겹친 결과입니다. 최종 PASS에는 두 검증이 모두 PASS여야 한다는 결합 조건을 유지했습니다. 남은 시간 대부분은 모델 실행 99–152초이며 실행마다 달라집니다.

승인 후 반영 T31은 **검증 환경에서 9.6초**, 게이트 재대조는 **별도 측정 38–63초**입니다. 각본은 승인 후 전체를 약 50–76초로 잡았습니다. 하나의 실제 콘솔 승인 실행에서 잰 값은 아닙니다. 역할마다 리허설 하나를 허용하는 API·콘솔 변경은 테스트로 확인했고 실제 콘솔 경로는 계획 0건이라 미실행입니다. [시간 원본](../evidence/s2-timing/README.md)

### 발견한 결함

- **가려진 diff:** 모델에 보여 준 출력의 비밀 마스킹 때문에 코드 문맥까지 바뀌어 diff 적용이 실패했습니다. 제출 diff를 실제 작업 공간 diff의 마스킹 결과와 대조한 뒤, 일치하면 원래 diff를 산출물로 받습니다.
- **ESO 버전:** 목적지에 없는 `v1beta1` API가 이미지 롤아웃 뒤에 실패했습니다. 목적지 API 버전을 검증하고, T31은 이미지 반입 전에 Kubernetes 서버 측 dry run을 수행합니다.

### 사람 검토 요청 — 판정 규칙은 별도 변경

시간 최적화와 별개로 `verify.py`의 규칙 6개와 검증 Job 내용도 바뀌었습니다. **검토 완료·팀 승인으로 표시하지 않습니다.** 자세한 전후·오류 코드·이유는 [S2 전체 기록의 바뀐 판정 규칙](../evidence/s2-full/README.md#바뀐-판정-규칙-검토용)에 있습니다.

| 규칙 | 바뀐 경계 |
|---|---|
| 비밀 경로 | 목적지 프로필 밖 경로 거부 |
| OpenBao HCL 파싱 | 읽지 못한 stanza를 통과시키지 않음 |
| OpenBao 권한 | read/list 밖 권한 거부 |
| Kubernetes 이름·네임스페이스 | T31과 같은 대상 범위 제한 |
| 버킷 Resource | 프로필의 첨부 버킷 ARN과 키에 한정 |
| ExternalSecret API 버전 | 목적지 ESO가 지원하는 버전과 대조 |

동작 검증도 버킷 정책의 OBJ-01–06, 앱의 실제 쓰기·읽기·비밀 주입·다른 SA 접근 거부, 원래 코드의 실패 대조를 포함하도록 바뀌었습니다. 각 규칙과 동작 검증의 기대값을 직접 검토해야 합니다.

## 4. 차가운 PgBouncer 예열 — `48a8537`

최소 연결을 10→20으로 늘리고 유휴 연결을 닫지 않도록 했습니다. 리셋에 예열을, 사전 점검에 연결 수 확인을 넣었습니다. PgBouncer를 일부러 재시작한 뒤 **예열 51초 → 정방향 48.3초 DONE**, 세 단계 오류 0·p95 639–701ms였습니다.

역방향은 오류가 없어도 **표본 90/100 부족으로 10%에서 복귀**했습니다. Cloudflare 가중치 변경 직후 대상 몫은 3.9–9.2%였고 40초 안에 표본 100건을 못 모을 수 있었습니다. 100% 변경 후에도 한 실행에서 25초 동안 75%가 옛 쪽으로 갔습니다. [차가운 상태 원본](../evidence/shift/pgbouncer-warm-pool-20261103/README.md)

**선택한 다음 변경:** 대기 시간을 늘리지 않고 10% 단계 쓰기 속도를 60→120/s로 올립니다. 관측 비율이 유지된다면 100건 확보는 약 9–21초로 계산되지만 **재시험 결과가 아닙니다**. 표본 100건·오류율 1%·p95 1,500ms 판정 기준은 유지합니다. 코드 `dd85cef`는 `pending/shift-probe-rate-120`에 있으며 미배포·왕복 재시험 대기입니다.

S4의 앞단 되돌리기는 판정 없이 LB를 옮기는 경로여서 이 표본 게이트를 거치지 않습니다. 이것이 실제 DB failback 전체 검증을 대신하지는 않습니다. S3 정방향 SHIFT에는 표본 판정이 적용됩니다.
