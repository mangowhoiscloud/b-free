## D-01. GCP 고객 환경을 P0 연결 뒤에 세움

**스펙.** AWS에서 GCP로 옮기는 이전은 비목표이고 P2입니다(§4). §4 목표의 마지막 줄은 "설계는 목적지 무관"입니다. 괄호 안의 배포판 이름은 D-21이 바꿉니다.

**제안.** 실제 컷오버와 되돌리기가 1회씩 끝난 뒤(일정상 11/5)에만, GCP에 GKE(Autopilot 우선)를 세웁니다(D-21). 같은 통제 시험(T14)을 돌려 통제 비교표에 세 번째 열을 만듭니다. 돌리지 못한 통제는 UNKNOWN으로 그대로 보입니다. AWS에서 GCP로 실제 컷오버를 하는 일은 P2 그대로입니다.

**늘어나는 작업.** `network/gcp`, `cluster/gke`, `ci_identity/gcp`, `envs/target-gcp`, GCP용 통제 시험 실행, 삭제 절차입니다. GKE에도 온프렘과 같은 랜딩 존을 설치합니다(D-23). 객체 저장은 온프렘과 같은 S3 호환 저장소(후보 Rook-Ceph RGW, 제안 D-22, 검증 중), 비밀은 온프렘과 같은 금고입니다. 비용 상한은 GKE 클러스터 2일분으로 둡니다. GKE 요금은 채택할 때 확인합니다.

**반론(리뷰).** 심사위원 · 팀원 리뷰는 P2로 내리자고 했습니다. 킥오프가 "하나를 깊게"를 강조했고, GCP 장면이 270초 각본에 없고, 인프라 · CI 담당이 가장 긴 경로의 첫 작업(T1, T6)을 맡기 때문입니다. 소재 판정은 환경 없이 계산으로도 보일 수 있습니다. 회의에서 이 반론과 함께 정합니다.

## D-02. Harbor를 리허설 실행 계층으로 씀

**스펙.** 런타임은 직접 띄운 리허설 네임스페이스이고, Harbor는 평가 전용(P1)입니다(§8.4). 역할 확정은 에이전트 · 리허설 담당이 합니다(§12).

**결정.** 리허설 1회를 Harbor Trial 1회로 돌립니다. Harbor 환경 어댑터가 리허설 네임스페이스를 만들고, 검증기는 별도 검증 네임스페이스에서 돌립니다. 에이전트 루프는 Trial마다 뜨는 자격 없는 Pod에서 돕니다(`docs/architecture/07-runtime-mesh-observability.md` 3절). 스펙의 격리 규칙(§8.4 표)은 D-12의 예외와 함께 지킵니다. 같은 경로를 T26 평가에도 씁니다. §12가 이 결정을 영역 담당에게 맡겼으므로 편차라기보다 미정 항목의 결정이며, 21:00 회의에서 공유합니다.

**늘어나는 작업.** T15a(어댑터)와 T26a(보상 조작 시험)입니다. T15는 T15a를 선행으로 갖습니다. 채택하면 `SPEC-TRACE.md` 4절에 두 줄을 더합니다.

**되돌림 기준.** 11/4 18:00까지 실제 목적지에서 다음이 한 번에 돌지 않으면 스펙 방안 1로 돌아갑니다: 네임스페이스 생성, 에이전트 Job 기동, 도구 계층을 거친 exec와 파일 전송, Trial 취소와 종료, 증거 수거, 분리 검증, 삭제(`docs/architecture/07-runtime-mesh-observability.md` 3절). 두 실행 경로는 리허설 러너 뒤의 같은 인터페이스(`start`, `exec`, `verify`, `stop`)를 구현합니다. 그래서 상태 머신, API, 도구 계층은 바뀌지 않습니다.

## D-03. 거버넌스 팩과 소재 사전 심사

**스펙.** 데이터 소재는 "얕게: 통제 GOV-01로만 표시"합니다(§2.1). 판정은 6개 통제로 고정하고, 규제는 매핑표로만 잇습니다(§8.5).

**제안은 둘로 나눕니다.**

- **D-03a 매핑표를 파일로 둠(스펙 범위 안).** §8.5의 매핑표를 (국가, 산업) 단위 YAML로 둡니다. 6개 통제의 시험과 합격선은 바꾸지 않습니다. GOV-01은 스펙대로 "표시"만 합니다.
- **D-03b 소재 사전 심사로 차단(스펙보다 넓음).** 이전 계획을 만들 때 GOV-01 판정을 돌리고, BLOCK이면 복제를 시작하지 않습니다. 상태 머신의 ANALYZE 전이 조건이 바뀌므로 데이터 · 컷오버 담당과 같이 정합니다. P0에는 넣지 않고, D-03a가 동작한 뒤 P1에서 판단합니다.

**판정 입력 규칙.** 데이터 종류(개인신용정보 여부 등)와 사업자 종류는 사람이 확정한 값만 씁니다. AI가 분류한 값은 판정 입력이 되지 않습니다. 근거 조항이 원문 확인 전(`unverified`)이면 결과는 PASS나 BLOCK이 아니라 NEEDS_HUMAN입니다. 원문 확인은 T23입니다.

**한계.** 법률 판단이 아닙니다. 정해진 규칙이 정해진 입력에 같은 답을 내는 장치입니다. 근거는 저장소 밖 팀 연구 폴더의 `deliverables/2026-11-02-governance-pack-region-migration.md`입니다.

## D-04. 첨부 파일 이전을 컷오버와 되돌리기에 넣음

**스펙.** 첨부 저장소는 "설정 교체(엔드포인트)"입니다(§7.3). 컷오버 2단계는 "모든 진입점에서 새 업무 쓰기"를 막지만, 컷오버 순서의 비교와 복제는 DB만 다룹니다(§8.6).

**공백.** 엔드포인트만 바꾸면 S3의 기존 첨부가 목적지 S3 호환 저장소(후보 Ceph RGW, 제안 D-22, 검증 중)로 옮겨지지 않습니다. 이전 뒤 옛 메시지의 첨부 링크가 깨집니다. 되돌리기 때도 목적지에서 올린 첨부가 출발지에 없습니다.

**제안.** 객체 저장소에는 덧붙이기만 하고, 첨부의 업무 상태는 모두 DB에 둡니다. DB에는 복제, 펜싱, 영수증이 이미 있으므로 첨부도 그 위에 올립니다. 2026-11-02 팀원 메모("설계 추가 제안" 4절, https://app.notion.com/p/40c8bee9ada48029a376dea2d411db1a)의 지원 계약을 받아 고쳤습니다.

1. **앱 계약.** 첨부마다 논리 ID와 클라이언트 멱등 키(UNIQUE)를 둡니다. 객체 키는 내용의 SHA-256(`att/<sha256>`)입니다. 같은 내용은 같은 키라서 재전송이 중복을 만들지 않고, 덮어쓰기가 생기지 않습니다. 교체는 새 행과 새 키, 삭제는 DB의 `deleted_at`입니다. 객체를 실제로 지우는 일은 이전 · 복구 보존 기간이 끝난 뒤이며 P0에는 없습니다(`apps/demo/README.md`).
2. **업로드 순서.** 객체 저장 → 앱이 SHA-256 확인 → DB에 첨부 행 commit(참조 확정)입니다. 행에는 객체를 올린 저장소 `store_id`를 적습니다. DB와 객체 저장소를 하나의 트랜잭션으로 묶지 않습니다. 객체만 있고 행이 없으면 참조 없는 객체로 남습니다. 이것은 무해하고 정리는 나중에 합니다. 행 commit의 응답을 잃으면 같은 멱등 키로 조회합니다.
3. **변경 기록.** 첨부 행 테이블이 곧 변경 기록(outbox)입니다. 행은 INSERT와 `deleted_at` 갱신뿐이라 논리 복제로 그대로 옮겨집니다. 별도 outbox를 두지 않습니다.
4. **저장소 세대.** 표 `attachment_store(active_store, generation, frozen, freeze_watermark)`를 둡니다.
   - 첨부 행 INSERT 트리거는 `frozen`이거나 행의 `store_id`가 `active_store`와 다르면 거부합니다.
   - 컷오버 뒤에는 `active_store`가 목적지입니다. 옛 환경에서 S3에 올리고 늦게 확정하려는 행은 거부됩니다. 클라이언트는 활성 환경에서 다시 올립니다. 되돌리기도 같은 규칙을 반대로 씁니다.
   - 이 표는 양쪽 DB에 따로 두고 발행(publication)에서 뺍니다. 목적지 행은 준비 단계에서 `frozen = true`로 만들어 둡니다.
5. **동결은 DB가 직렬화합니다.** Executor는 한 트랜잭션에서 `LOCK TABLE attachments IN SHARE ROW EXCLUSIVE MODE`를 잡습니다. 그다음 `UPDATE attachment_store SET frozen = true, freeze_watermark = <확정 첨부 행의 최대 순번>`을 하고 commit합니다. 이 잠금은 INSERT의 잠금과 충돌하므로, 진행 중이던 INSERT가 먼저 끝납니다. 그 뒤의 INSERT는 트리거가 거부합니다. 앱은 "첨부 일시 중지"를 안내하고, 같은 멱등 키로 다시 시도합니다. 그래서 진행 중인 업로드가 끝났는지를 시간 초과로 추측하지 않습니다.
6. **불변성.** UPDATE 트리거가 key, sha256, `store_id`의 변경을 막습니다. `deleted_at`은 NULL에서 시각으로만 바뀝니다. 앱 역할은 `attachment_store`와 트리거에 아무 권한이 없습니다. 논리 복제 적용은 일반 트리거를 부르지 않으므로 복제로 온 행은 막히지 않습니다. 앱 세션은 `session_replication_role`을 바꾸지 못합니다.
7. **복사와 대조.** SHIFT 전에 사전 복사합니다. SHIFT 시작 때 동결을 commit하고 차이분을 복사합니다. 컷오버 1단계 전, 쓰기 정지 밖에서 모든 확정 참조를 대조합니다. 대상에 있고, SHA-256이 같고, 앱 역할로 읽혀야 합니다. 메시지 쓰기는 계속됩니다.
8. **복사 상태.** 표 `attachment_copies(key, target_store, verified_sha256, verified_at)`에 키별 검증 결과를 둡니다. 복사 Job은 "확정 참조 집합 빼기 검증된 복사 집합"을 매번 다시 계산합니다. ID 커서를 쓰지 않습니다. 늦게 commit된 낮은 ID를 놓치기 때문입니다. 그래서 Job이 중간에 죽어도 다시 시작할 수 있습니다.
9. **전환 조건.** 1단계 전 대조에서 아래가 하나라도 어긋나면 컷오버를 시작하지 않습니다. 컷오버 5단계에서는 동결 watermark를 넘는 확정 행이 없는지만 봅니다. 결과는 영수증 `objects[]`에 대조 시각, watermark와 함께 넣습니다.
   - 동결 뒤 모든 확정 참조(삭제 표시 없는 것)가 대상 저장소에 있고, SHA-256이 같고, 앱 역할로 읽힘
   - 대상 버킷의 접근 정책 시험(익명 거부, 앱 역할 읽기)이 통과. 게이트의 S3 통제 시험을 다시 씀
   - `attachment_copies`에 검증되지 않은 확정 참조 0
10. **동결 해제는 효과입니다.** 정한 지점에서만 풉니다. 해제마다 효과 원장(D-19)에 한 행을 남깁니다.

| 시점 | 해제 방법 |
|---|---|
| 컷오버 8단계 뒤 | 같은 트랜잭션에서 목적지 `active_store`를 목적지로 바꾸고 동결 해제 |
| ABORT_PRE_WRITE 뒤 | 출발지 동결 해제. `active_store`는 그대로 |
| SHIFT 실패(가중치 0) 뒤 | 출발지 동결 해제 |
| 되돌리기 완료 뒤 | 출발지 `active_store`를 출발지로 둔 채 동결 해제 |

11. **버전 ID를 비교하지 않습니다.** S3와 목적지 저장소의 버전 ID는 다릅니다. 판정 기준은 논리 ID, 내용 해시, DB 참조입니다. multipart ETag도 저장소마다 달라 쓰지 않습니다.
12. **우회 쓰기 경로를 없앱니다.** presigned URL, multipart 업로드, 앱 밖 직접 쓰기를 쓰지 않습니다. 첨부 크기 상한을 둡니다(예: 5 MB, 한 번의 PUT). T16 정적 탐지가 위반을 찾습니다.
13. **WATCH 동안 역복사와 되돌리기.** 전환 확정 뒤 새 첨부는 목적지 저장소에 쌓입니다. 그 행은 역방향 복제로 출발지 DB에도 옵니다. 출발지 쪽 Job이 새 키를 S3로 계속 복사합니다. 되돌리기 때는 목적지에서 동결하고 barrier를 거칩니다. 그다음 모든 활성 참조를 S3와 전체 대조합니다(존재, SHA-256, 앱 읽기 권한). 하나라도 읽지 못하면 DB가 살아 있어도 SAFE_HOLD입니다. 메시지만 돌아오고 첨부가 빠진 상태는 되돌리기 완료가 아닙니다.
14. **자격.** 복사 Job은 언제나 AWS 쪽(출발지 클러스터)에서 돕니다. S3는 앱 전용 역할로, 목적지 저장소는 첨부 버킷 하나에 묶인 자격으로 접근합니다. 후보 Rook-Ceph면 ObjectBucketClaim이 버킷마다 만드는 사용자입니다(확인 필요). 온프렘에는 AWS 자격이 들어가지 않습니다.

**인수 시험.**
- 동결 commit과 동시에 INSERT를 보냄(동결 경쟁): INSERT가 먼저 끝나거나 거부되고, 확정 행이 watermark를 넘지 않음
- 업로드 도중 동결해도 확정된 첨부가 유실되지 않음
- 컷오버 뒤 옛 환경에서 늦게 확정하려는 행이 거부되고, 활성 환경 재시도로 확정됨
- 첨부 행의 key, sha256, `store_id` 변경과 `deleted_at` 되돌리기가 거부됨
- 같은 요청을 다시 보내도 중복 참조가 생기지 않음
- 복사 Job을 중간에 죽이고 다시 시작해도 빠진 키가 없음
- 목적지에서 만든 새 첨부까지 출발지로 돌아옴
- 객체 누락, SHA-256 불일치, 검증되지 않은 복사가 있으면 전환이 막힘
- 객체 수와 총 용량(예: 100개 · 1,000개)별 사전 복사와 차이분 복사 시간을 측정

**줄이는 범위.** 11/5까지 위 계약이 준비되지 않으면 데모는 WATCH 동안 신규 첨부를 막습니다. 화면에는 "WATCH 신규 첨부 복구 미지원"을 보입니다. 기존 첨부의 이전과 대조는 그대로 합니다.

**늘어나는 작업.** 첨부 복사 Job(사전 복사, 차이분, 역복사, `attachment_copies`)은 따로 작업 줄을 둡니다. 번호는 회의에서 정합니다. 동결 트리거와 `store_id`는 데모 앱(T4, T22), 동결 · 해제 효과는 Executor(T12, T20)입니다.

**대가와 측정.** SHIFT부터 전환 확정까지 첨부를 올릴 수 없습니다. 길이는 1–2분으로 추정하며 측정 전입니다. 스펙의 쓰기 정지 정의(첫 업무 쓰기 제한부터 마지막 경로 ACK까지)를 그대로 쓰면 이 구간도 쓰기 정지에 들어갑니다. 그래서 측정은 둘로 나눠 모두 공개합니다. "DB 쓰기 정지"(컷오버 1–8단계)와 "첨부 업로드 정지"(동결 commit부터 해제까지)입니다. "전체 쓰기 정지 5초"라고 말하지 않습니다. NFR-1의 5초 목표를 DB 쓰기 정지에만 적용할지는 이 제안과 함께 정합니다. 기능 축소이므로 데모에서 숨기지 않습니다.

## D-05. FR-1 수집기를 맡을 작업을 정함

**공백.** FR-1(읽기 전용 수집)을 만드는 작업이 §11.1에 없습니다. T14와 T16이 수집 결과를 쓰고, 상태 머신의 COLLECT도 이 출력이 끝나야 넘어갑니다.

**제안.** 새 작업 T30(수집기)을 만들고 11/3 계약 목록에 "수집 출력"을 넣습니다(`docs/plans/2026-11-03-to-07.md` 3절). 담당 후보는 보안 통제 · 게이트(T14가 주 소비자)입니다. 에이전트 · 리허설 담당은 이미 P0가 많아 뺐습니다. 완료 기준에는 "수집 자격으로 쓰기가 거부된다"를 넣습니다.

## D-06. 도구 계층을 구조화한 작업으로 바꿈

**스펙.** `rehearsal.exec`는 리허설 네임스페이스 안에서 명령을 실행하고, 파괴적 명령은 도구 계층의 차단 목록으로 막습니다(§8.3). 차단 목록을 어떻게 구현할지는 정하지 않았습니다.

**문제.** 자유 문자열 명령을 받는 한, 차단 목록은 변형으로 우회됩니다. 프로토타입의 정규식 차단 목록(`platform/rehearsal/src/bravo_rehearsal/blocklist.py`)은 `rm -r -f`, `kubectl -n x delete ns x`, `find -delete`, `curl -X DELETE`, base64 실행으로 뚫렸습니다(전문가 리뷰 재현). 또 K8s RBAC는 허용된 exec 안에서 일어나는 파일 삭제나 SQL을 막지 못합니다.

**제안.**

1. `rehearsal.exec`는 자유 명령을 받지 않고, 정해진 작업 목록만 받습니다. 예: `apply(manifest)`, `get(kind, name)`, `logs(pod)`, `write_file(path, content)`, `run_test(name)`. 각 작업은 (동사, 자원 종류, 네임스페이스)로 검사합니다. 목록에 없으면 거부하고 기록합니다.
2. 문자열 차단 목록은 지웠습니다. 대신 파괴적 동사(delete, exec 등)를 이름 붙여 거부해, §8.3이 요구한 "도구 계층에서 차단"과 콘솔의 차단 기록을 그대로 남깁니다.
3. 데이터 쪽 마지막 경계는 자격입니다. 리허설용 OpenBao 경로, 목적지 저장소의 시험 버킷 자격(D-22), DB 역할에는 삭제 권한이 없습니다.
4. apply는 정확한 (apiVersion, kind)과 네임스페이스 범위 자원만 받고, Pod 정의의 권한 필드(서비스 계정, 토큰, 호스트 접근, capability, 비밀 참조)를 검사합니다. 기본값이 적용된 최종 객체에 같은 정책을 admission으로도 강제할 계획입니다(T3, 아직 없음).

**한계.** `write_file`로 쓴 코드를 `run_check`가 실행하므로, 리허설 Pod 안의 임의 코드 실행은 이 계층이 막지 못합니다. 그 경계는 Pod 격리(토큰 없음, Pod Security, NetworkPolicy)입니다.

**영향.** 에이전트의 자유도가 줄어 S2 수정 성공률이 낮아질 수 있습니다. T26에서 수치로 확인합니다.

**반영.** 스펙이 차단 목록의 구현 방식을 정하지 않았으므로 구현 선택(`README.md` 규칙 5)으로 보고, 영역 담당 승인으로 프로토타입에 반영했습니다(`platform/rehearsal/src/bravo_rehearsal/tool_layer.py`, 시험 `tests/test_tool_layer.py`). 회의에서 공유합니다.

## D-07. 리전 이전은 설계 문서에만

**스펙.** 리전 이전은 스펙에 없습니다.

**제안.** 데모 장면에 넣지 않습니다. 설계 문서에 "같은 판정 장치를 리전 이전에 쓰면 어떻게 되는가"만 적습니다. 실제 이전은 P2입니다. D-03b가 기각되면 이 제안도 함께 기각됩니다.

**왜 장면에서 뺐나.** 리뷰에서 세 가지가 나왔습니다. 첫째, 근거 조항이 원문 확인 전이면 정답은 BLOCK이 아니라 NEEDS_HUMAN입니다. 둘째, 개인정보가 없는 부분만 옮기는 분할 이전은 가능하고, 반대 방향(도쿄에서 서울)은 사람이 판단할 사안입니다. 셋째, 일본 심사위원 앞에서 "서울에서 도쿄는 차단"을 보이는 장면은 단순화로 읽힐 수 있습니다.

## D-08. 이전 완수 증거표를 DONE 보고서로 냄

**스펙.** WATCH에서 통제 재시험이 PASS이면 DONE입니다(§8.2). 장애나 재시험 실패면 FAILBACK입니다.

**제안.** 전이 조건은 스펙 그대로 둡니다. DONE으로 넘어갈 때 `docs/architecture/03-migration.md` 5절의 증거표를 채운 보고서를 만듭니다. 빠진 증거는 "미완"으로 표시하고 사람에게 알립니다. 증거표의 항목을 DONE 전이 조건으로 올리는 것은 P1에서 따로 정합니다.

## D-09. 컷오버 6단계를 확정 지점 앞뒤로 나눔

**스펙.** 1–5단계 실패는 ABORT_PRE_WRITE, 6단계 이후 실패는 FAILBACK입니다(§8.6). Executor 결과는 DONE, ABORT_PRE_WRITE, SAFE_HOLD입니다.

**문제.** 실제 되돌릴 수 없는 지점은 6단계 안의 "전환 확정 기록"입니다. 그 앞에서 역방향 구독 켜기가 실패하면 목적지에는 아직 업무 쓰기가 없습니다. 그런데 표대로면 FAILBACK으로 가고, FAILBACK은 없는 역방향 barrier를 기다리다 SAFE_HOLD에 빠집니다.

**제안.** 6단계를 6a(정방향 apply 정지 확인, 미리 만든 역방향 구독 켜기)와 6b(전환 확정 기록)로 나눕니다. 6b 전 실패는 ABORT_PRE_WRITE, 6b 뒤 실패는 FAILBACK입니다. Executor 결과에 `FAILBACK_REQUIRED`를 더해 상태 머신이 분기를 추측하지 않게 합니다. 스펙 v0.2에 반영을 요청합니다.

## D-10. 가중치 단계 API와 콘솔의 LIVE · RECORDED 표시

**공백.** §8.9에는 가중치 10, 50, 100%를 바꾸는 API가 없습니다. 데모의 사전 실행 장면과 라이브 장면을 화면에서 구분하는 규칙도 없습니다.

**제안.**

- `POST /v1/plans/{id}/weights`(목표 가중치, `Idempotency-Key`) → 반영 시각, 관측 비율. Edge 제어 코드는 `platform/api/edge/`에 두고 작업 주인은 콘솔 · 관측 · Edge(T17)입니다.
- SSE 이벤트와 콘솔 패널마다 `mode`(`live`, `recorded`)와 `run_id`, 시각을 둡니다. 사전 실행 기록은 언제나 `recorded`로 보입니다.

## D-11. 예외 승인도 승인 API의 단계로 받음

**공백.** §8.5는 대체 불가 예외를 "승인 · 기간 · 대체 통제와 함께" 표시하라고 하지만, 받는 API가 없습니다.

**제안.** `POST /v1/plans/{id}/approvals`의 `stage`에 `exception`을 더합니다. 입력은 통제 ID, 사유, 대체 통제, 만료입니다. 예: `istio-system`의 Pod Security 예외(D-15).

스펙 §7.5대로 Tailscale operator 프록시를 쓰면 그 네임스페이스도 privileged 예외가 됩니다. D-16을 채택하면 이 예외는 사라집니다. `cloudflared` 이미지는 `restricted`를 지킬 수 있기 때문입니다(`docs/architecture/02-network.md` 6절).

## D-12. 리허설 NetworkPolicy에 필요한 예외

**스펙.** 리허설 네임스페이스는 NetworkPolicy 기본 거부이고, 네임스페이스 안 통신만 허용합니다(§8.4). 검증 Job은 검증 대상 Pod에만 접근합니다(§7.5).

**문제.** 이대로면 DNS, 목적지 프로필(시험용 OpenBao 경로, 목적지 저장소의 시험 버킷. 후보 Ceph RGW, 제안 D-22, 검증 중), 검증 Job의 접근이 막혀 리허설이 돌지 않습니다. §8.4가 "목적지 프로필"을 넣으라고 한 것과 같은 절의 격리 규칙이 서로 부딪칩니다.

**제안.** 예외를 아래로 한정하고, 예외마다 격리 시험을 더합니다(`docs/architecture/05-agent-rehearsal.md` 3절).

| 주체 | 대상 | 포트 | 남는 위험 | 더하는 시험 |
|---|---|---|---|---|
| 리허설 Pod | kube-dns | 53 | DNS 질의로 정보 유출 | 외부 이름 해석이 실패하는지(CoreDNS 업스트림 차단 여부) |
| 리허설 Pod | 시험용 OpenBao 경로, 목적지 저장소 Service(시험 버킷) | 8200, 443(후보 RGW 기준, 확인 필요) | 같은 서비스의 다른 경로 · 버킷 접근 | 시험용 자격으로 운영 경로 · 운영 버킷 접근이 거부되는지 |
| 검증 네임스페이스 | 리허설 앱 포트, API 서버 | 앱 포트, 6443 | 검증 계정 권한 남용 | 검증 계정으로 리허설 밖 자원 쓰기가 거부되는지 |

D-02의 "격리 규칙 그대로"는 이 예외를 포함한 규칙을 뜻합니다.

## D-13. 승인 요약과 사후 리포트를 P0에서 템플릿으로

**스펙.** 에이전트의 할 일에 승인자용 요약과 사후 리포트 초안이 있습니다(§8.3).

**제안.** P0에서는 정해진 데이터(diff, 검증 결과, 통제 비교표)로 코드 템플릿이 만듭니다. AI 작성은 P1입니다. 같은 입력에 같은 요약이 나와 승인 화면을 시험하기 쉽고, P0의 AI 작업을 S2 수정 루프에 모으기 위해서입니다.

## D-14. 데모 이미지를 GHCR 공개 패키지로

**스펙.** 출발지 · 목적지 → GHCR은 "이미지 pull만, 읽기 전용 토큰"입니다(§7.5). 장기 키는 없습니다(NFR-6).

**문제.** GHCR는 비공개 패키지 pull에 classic PAT만 받습니다. 읽기 전용 토큰을 두면 장기 토큰이 각 클러스터에 들어가 NFR-6과 부딪힙니다.

**제안.** 데모 이미지를 공개 패키지로 두고 pull 토큰을 없앱니다. 이미지에는 비밀을 넣지 않습니다(gitleaks와 이미지 검사로 확인). 운영 권장 구성은 비공개 레지스트리와 단기 자격이라고 설계 문서에 적습니다.

## D-15. 플랫폼 클러스터에 Istio ambient(L4)와 OTel 관측 백엔드를 더함

**스펙.** §7.4의 컴포넌트 표와 §8.8의 인프라 구성에 서비스 메시와 관측 백엔드는 없습니다. 구현 선택이지만 인프라 · CI(T7)와 콘솔 · 관측(T18) 영역의 일이 늘어나므로 편차로 올립니다.

**제안.** 플랫폼 클러스터에만 Istio ambient를 L4로 넣고(waypoint 없음), 관측은 OTLP 하나로 모읍니다. 플랫폼 클러스터는 Amazon EKS입니다(D-21). 컷오버 경로(Executor)는 메시 밖에 둡니다. 설계는 `docs/architecture/07-runtime-mesh-observability.md`입니다.

**늘어나는 것.** istiod, istio-cni, ztunnel, 관측 백엔드 1개. 이 자원은 플랫폼 EKS의 관리형 노드 그룹 core와 agents(`docs/architecture/01-environments.md` 2절)에 나눠 놓입니다. `istio-system`의 Pod Security 예외가 하나 생깁니다.

**플랫폼별 설치 조건.** Istio ambient 플랫폼 요건 문서(1.31.3, 2026-11-02 조회)를 따릅니다.
- EKS: VPC CNI의 Pod 보안 그룹(security groups for Pods)을 쓰면 `POD_SECURITY_GROUP_ENFORCING_MODE=standard`를 명시합니다. `strict`에서는 VPC CNI가 링크 로컬 패킷을 잘못 보내 Pod 상태 프로브가 실패합니다.
- P0 노드는 t4g입니다. t 계열은 Pod 보안 그룹을 지원하지 않습니다(AWS EKS 문서 "Assign security groups to individual Pods", 2026-11-02 조회). 그래서 P0에서는 Pod 보안 그룹을 켜지 않습니다. 노드 종류를 바꿔 켤 때 위 값을 같이 둡니다.
- VPC CNI 네트워크 정책과 ambient의 공존(15008, 프로브 주소 `169.254.7.127`)은 T7에서 실측합니다.
- K3s: P0 메시는 플랫폼에만 있으므로 해당이 없습니다. 온프렘에 메시를 넣게 되면 설치 값에 `global.platform=k3s`를 줍니다. K3s의 CNI 설정 경로와 바이너리 경로가 표준과 다르기 때문입니다.

**되돌림 기준.** 11/4(수) 12:00까지 플랫폼 EKS(VPC CNI, 네트워크 정책 켬)에 ambient가 설치되고 mTLS와 인가 거부 시험이 통과하지 않으면 메시를 뺍니다. 관측(OTLP)과 상태 주입은 메시와 무관하게 남습니다.

## D-16. 환경 사이 연결을 Tailscale에서 Cloudflare Tunnel + Access 링크로 바꿈

**스펙.** 복제, 제어, 첨부 복사는 Tailscale ACL로 잇습니다(§7.5). 플랫폼에서 출발지 · 목적지로는 VPC 피어링이나 Tailscale입니다. T1은 VPC 2개와 피어링을 만들고, §8.8은 Tailscale을 플랫폼 · 온프렘 공용 cloud-init으로 설치합니다(클러스터 배포판은 D-21). 이 밖에 Tailscale을 쓰는 스펙 위치는 셋입니다.
- §6 S3 시작 조건: 논리 복제가 "Tailscale 경로로" 따라오고 있음
- §8.6 전환 전 쓰기 경로: SHIFT 동안 목적지 PgBouncer가 Tailscale로 출발지 DB에 씀
- T2: 온프렘 구축의 만들 것에 Tailscale 설치가 있음

스펙 v0.2를 낼 때 이 위치들을 D-16 경로(링크 `src-db`)로 바꿉니다.

**검토 이유.** 팀장(류지환)이 Tailscale의 신뢰성을 문제로 들어, 엔터프라이즈와 수상작의 하이브리드 연결 방식을 기준으로 다시 고르기로 했습니다. 후보는 제어 경로의 바깥 방향 클러스터 에이전트, 데이터 경로의 AWS Site-to-Site VPN, Cloudflare Zero Trust였습니다. 2026-11-02에 설계안이 나와 아래에 채웠습니다. 회의에서 정합니다.

**제안.** 설계안은 `research/platform-research/network-design-2026-11-02.md`이고, 저장소에 옮긴 설계는 `docs/architecture/02-network.md`입니다.
- 어느 환경에도 인바운드 포트를 열지 않습니다. 커넥터 하나(`cloudflared`)가 제어면과 데이터면을 함께 나릅니다.
- 제어면은 K8s API, PgBouncer 관리, DB 제어입니다. 데이터면은 논리 복제(5432)와 첨부 복사(목적지 저장소의 S3 API. 후보 RGW 기준 443, 제안 D-22, 확인 필요)입니다.
- 노출하는 고객 클러스터는 관리 Tunnel을 둡니다. 소비하는 클러스터는 `cloudflared access tcp` 링크로 상대 서비스를 로컬 이름으로 받습니다.
- Cloudflare Access가 링크마다 다른 서비스 토큰을 Service Auth 정책으로 확인합니다. 테넌트 하나에 앱 7개, 토큰 9개입니다.
- 호텔 NAT 뒤 온프렘이 새로 요구하는 포트는 없습니다. §8.7의 사용자 진입 Tunnel이 이미 7844 아웃바운드를 쓰기 때문입니다.
- AWS VPC는 사설 서브넷만 두고 VPC마다 Regional NAT 하나로 나갑니다. 노드 공인 IP와 VPC 피어링은 없습니다. 피어링은 비상 토글로만 남깁니다.
- 테넌트 모델을 함께 둡니다. 플랫폼 DB의 모든 행에 `tenant_id`와 RLS `FORCE`를 두고, Trial 토큰에 `tenant_id`를 더합니다.
- 배포는 각 클러스터의 Argo CD가 Git 저장소를 당겨 오는 방식입니다. 비공개 AWS 클러스터의 첫 설치만 VPC 안 CodeBuild가 한 번 합니다(`02-network.md` 14절).

**스펙 §7.5와 대응.**

| §7.5 행 | 스펙 방법 | D-16 방법 |
|---|---|---|
| 출발지 CNPG ↔ 목적지 CNPG | Tailscale ACL | 링크 `src-db`, `dst-db`. Access 정책은 토큰 `dst-src-db`, `src-dst-db`만. 복제 역할 + `verify-full` |
| 목적지 PgBouncer → 출발지 DB(컷오버 전) | Tailscale ACL | 링크 `src-db`(같은 토큰 `dst-src-db`). 앱 쓰기 역할 |
| 플랫폼 → 출발지 · 목적지 | VPC 피어링 또는 Tailscale | 링크 `*-k8s`, `*-db`, `*-pgb`. 토큰 `plat-*`. 수집 역할과 제어 역할은 K8s 서비스 계정과 DB 역할로 나눔 |
| 출발지 · 목적지 → GHCR | 바깥 방향 연결 | 같음. 고객 클러스터의 Git pull(`github.com` 443)이 더해짐 |
| 사용자 → 채팅 앱, 플랫폼 → Cloudflare API, 운영팀 → 콘솔, 에이전트 행 | Tunnel, API 토큰, 로그인, 게이트웨이 | 바뀌지 않음 |

**왜 이 수단인가.**

| 후보 | 판정 | 이유 |
|---|---|---|
| Cloudflare Tunnel + Access(`access tcp`) | 주 경로 | 7844 아웃바운드만 씀. 사용자 진입이 이미 같은 포트를 씀. Zero Trust Free 플랜이고 Tunnel 추가 비용이 없음 |
| AWS Site-to-Site VPN(GCP는 HA VPN) | 데이터면 폴백 | 중계 계층이 없어 지연이 가장 작다고 봄(추정). UDP 500과 4500이 필요하고, TCP 캡슐화 옵션은 문서에 없음. 호텔에서 UDP가 막히면 전부 끊김 |
| Cloudflare Mesh(구 WARP Connector) | 승격 경로 | L3라 장기 TCP 세션이 끝까지 보존됨. 노드에 설치하고 최소 3 vCPU라 t4g.large(2 vCPU)에 맞지 않음 |
| WireGuard 직접 | 제외 | 모든 패킷이 UDP. AWS 쪽에 UDP 수신 지점이 필요해 인바운드 0과 부딪힘 |
| 바깥 방향 클러스터 에이전트(Azure Arc, Rancher, Argo CD agent 등) | 패턴만 채택 | K8s API와 GitOps만 다룸. 5432와 첨부 저장소(S3 API)는 나르지 못한다고 봄(추정) |
| Git pull | 배포에 채택 | 443 아웃바운드만 씀. 커밋 왕복이 초 단위 이상이라 컷오버 명령에는 맞지 않음 |

바깥 방향 클러스터 에이전트는 관리 대상이 먼저 나가 연결하고, 중앙은 그 연결로 요청합니다. `cloudflared`도 같은 종류의 커넥터입니다. 다른 점은 임의의 TCP를 나른다는 것입니다. 그래서 커넥터 하나로 API, DB, S3를 모두 다룹니다.

**비용.** 단가는 설계안이 인용한 AWS Price List 파일과 Cloudflare 가격 페이지입니다(2026-11-02 조회).
- Cloudflare는 Zero Trust Free(50명, 검색 결과 요약으로만 확인)이고, Tunnel 추가 비용은 없습니다. LB 월 약 $5는 기존 그대로입니다.
- Regional NAT는 활성 AZ마다 과금됩니다(AWS VPC 요금 페이지, 2026-11-02 조회). 활성 AZ 4–5개면 하루 약 $6.1–7.7이 더해집니다(추정). AZ마다 NAT Gateway를 두는 안과 같거나 조금 많습니다. 그래도 고르는 이유는 공개 서브넷이 없고 AZ 확장이 자동이기 때문입니다.
- 노드 공인 IPv4 5개(하루 $0.60)는 빠집니다.
- AWS 전체는 하루 약 $15.4에서 약 $21–22.5로, 6일 약 $92에서 약 $125–135로 늡니다(추정, D-21의 EKS 구성 기준, `docs/architecture/01-environments.md` 6절).
- 폴백 S2S VPN을 켜면 연결당 하루 $1.20이 더해집니다. 인증서 인증에 Private CA가 필요하면 월 $400 또는 단기 모드 $50입니다.

**폴백.**

| 구분 | 기본 | 폴백 |
|---|---|---|
| 제어면, 동기 | 관리 Tunnel + 링크 | 같은 구성. 막히면 업링크 교체(LTE 또는 5G 공유기) |
| 제어면, 비동기(배포) | 각 클러스터의 Argo CD pull | 플랫폼 안 일회용 runner가 링크로 push |
| 데이터면 | 같은 Tunnel + 링크 | AWS S2S VPN. N16이 11/4 18:00까지 통과했을 때만(아래 규칙 5). GCP는 HA VPN. CGW는 암호화 전에 단편화하게 설정 |
| 마지막 | 사전 실행 기록 재생(`recorded` 표시, D-10) | 없음 |

4. 7844가 열려 있어도 링크가 시험에 실패할 수 있습니다. N5에 두 번 연속 실패하거나 N11이 합격선을 넘으면, 데이터면을 폴백으로 옮깁니다(설계안의 규칙).

**남는 위험.**
- 커넥터가 다시 붙을 때 장기 TCP 세션(5432)이 끊길 수 있습니다. 슬롯이 `max_slot_wal_keep_size` 안에서 WAL을 지키면 이어서 받습니다. 넘으면 슬롯이 `lost`가 되고, 컷오버를 막고 재동기화합니다(`03-migration.md` 4.1, N5c).

- Cloudflare edge가 평문을 볼 수 있습니다(추정). 링크 위 TLS를 필수로 하고 N6으로 확인합니다.
- 서비스 토큰은 7일짜리 비밀로 남습니다. NFR-6(장기 키 없음)과 완전히 맞지는 않습니다. 회전 연습은 11/6에 하고, 11/7–11/8에는 회전하지 않습니다.
- 공유 Executor가 침해되면 모든 테넌트의 링크에 닿습니다. 근본 해결은 테넌트별 Executor입니다.

| 사용자 진입 | 데모 중 대안 없음. 그렇다고 밝힘 |
| 운영자 접근 | AWS SSM 포트 포워딩으로 플랫폼에 닿음. 비상용이고 기록이 남음(N17) |
| 사람 승인 | 불가. 계획은 SAFE_HOLD나 AWAIT_APPROVAL에 머묾 |
| 환경 사이 링크 | 새 컷오버를 시작하지 않음 |
| 진행 중 컷오버 | SAFE_HOLD |

**정한 것(이전에 열린 항목).** `edge_link`는 비밀이 아닌 것(Tunnel, DNS 레코드, Access 앱, 정책)만 Terraform으로 만듭니다. 서비스 토큰과 Tunnel 토큰은 부트스트랩 스크립트가 Cloudflare API로 만들어 AWS Secrets Manager에 바로 씁니다. 온프렘 쪽은 운영자가 런북대로 온프렘 OpenBao에 한 번 넣습니다. 그래서 상태 파일에 비밀이 남지 않습니다(`infra/README.md`).

**열린 결정.** O1–O13과 설계안이 다루지 않은 항목은 `docs/architecture/02-network.md` 14절에 있습니다.

**제안(2026-11-02, 사용자 진입 쪽 보완, 정하지 않음).** 근거는 `docs/architecture/15-multicloud-traffic.md`입니다.
- F1의 "LB monitor가 다른 pool로 넘김"은 앱 장애를 잡는다는 보장이 없습니다. Cloudflare 문서의 Tunnel 끝점 모니터 예시는 `cloudflared` 도달만 확인합니다. 앱 품질 판정은 Executor가 합니다. 시험 T-E5로 확인합니다.
- 대표 CNAME을 LB 아래에 남깁니다. 같은 이름이면 LB가 우선하고, LB를 끄면 그 CNAME이 응답합니다(Cloudflare 문서). 스펙 §8.7의 "비상 경로는 DNS 전환"이 이 레코드입니다. 지금 모듈은 LB를 켜면 CNAME을 지웁니다.
- 비용의 "LB 월 약 $5"는 공식 가격 페이지의 시작 금액입니다. GKE pool을 더해 끝점이 셋이 되면 늘 수 있습니다(확인 필요).
- 클러스터를 넘는 메시(ClusterMesh, Istio 다중 클러스터, Submariner, Skupper)는 사용자 경로에 쓰지 않습니다. 모두 인바운드나 클러스터 사이 망을 요구해 이 편차의 인바운드 0과 부딪힙니다.

## D-17. 플랫폼을 단일 노드에서 3-AZ RKE2 HA로

**상태: D-21로 대체(2026-11-02).** 플랫폼은 EKS가 됐습니다. 제어면은 AWS가 3 AZ에서 운영하고, 노드는 관리형 노드 그룹 core(3 AZ)와 agents입니다. 아래 본문은 이력으로만 남깁니다. 구현하지 않습니다.

**스펙.** 플랫폼은 "EC2 1대 + RKE2 단일 노드"입니다(§7.2).

**제안.** 전용 server 3대(AZ마다 1, taint), core 워커 3대(AZ마다 1), agents 워커 1대로 둡니다(`docs/architecture/01-environments.md` 2절). etcd를 워크로드와 떼고, AZ 하나를 잃어도 제어와 플랫폼 DB가 버티게 하기 위해서입니다. 예선 Railshot의 단일 server 구성에서 겪은 불안정과 etcd 운영 가이드가 근거입니다.

**비용.** 플랫폼만 하루 약 $11(단일 노드 대비 약 $7 증가). AWS 전체 6일 약 $97.

## D-18. 운영자 MCP 서버를 더함

**스펙.** 운영팀은 콘솔로 환경을 등록하고 이전을 시작합니다(§7.1). 플랫폼 API는 REST입니다(§8.9).

**결정.** 팀장(류지환)이 11/2에 "앞단은 MCP"로 정했습니다. REST와 콘솔은 그대로 두고, 운영자의 MCP 클라이언트가 부르는 **운영자 MCP 서버**를 더합니다. 이 서버는 화면도 첫 관문도 아니므로 "앞단" 대신 부르는 쪽으로 이름을 붙였습니다. 리허설 에이전트가 부르는 도구 계층 MCP 서버와 구분됩니다. 설계는 `docs/architecture/08-operator-mcp.md`입니다.
- 운영자는 MCP로 환경 등록, 계획, 리허설, 게이트, 조회를 부릅니다. 도구는 일곱 개입니다.
- 트래픽 전환, 컷오버, 되돌리기는 MCP로 시작하지 않습니다. 승인 뒤 사람 운영자가 콘솔에서 시작합니다. 스펙 §8.2가 이 구간을 "실행 · 코드만 (AI 관여 없음)"으로 두기 때문입니다. 승인은 무엇을 할지에 묶이고, 언제 할지에는 묶이지 않습니다.
- 사람 승인(FR-7)과 보안 보류 해제(D-20)도 MCP에 두지 않고 콘솔에서만 합니다.
- MCP 결과에는 고객 저장소 원문을 넣지 않습니다. 서버가 만든 상태, ID, 이유 코드, 개수, 콘솔 증거 링크만 돌려줍니다.
- 인증은 Cloudflare Access Managed OAuth입니다. MCP와 콘솔은 서로 다른 Access 앱입니다. 주체는 JWT의 `(iss, sub)`이고 이메일은 표시용입니다.

**배치.** API와 같은 이미지를 별도 Deployment `operator-mcp`(`bravo-control`, 레플리카 2)로 띄우고 `/mcp`만 켭니다. 메시 신원과 전용 DB 역할 `operator_mcp`를 따로 둡니다. 이 역할에는 승인 · 보류 표의 쓰기 권한이 없고, 실행 요청은 `rehearsal`, `gate` 종류만 INSERT할 수 있습니다. 플랫폼의 Tunnel 커넥터는 `cf-edge` 네임스페이스에 두고 메시에 등록합니다.

**늘어나는 것.** Deployment 하나(메모리 요청 약 0.5 GiB, 추정), 도구 일곱 개, `GET /v1/plans/{id}`, DB 역할 하나, `principals` 표, Access 앱 하나(MCP용, 콘솔 앱과 따로).

**되돌림 기준.** 11/3에 읽기 도구로 Claude Code 실제 연결을 먼저 확인합니다. 11/5(목) 18:00까지 Claude Code가 Access Managed OAuth로 붙지 않으면 데모는 콘솔로만 합니다. S1–S4의 인수 조건에는 들어가지 않습니다.

## D-19. Executor에 효과 원장과 인계 차단을 더함

**스펙.** 응답을 잃으면 같은 호출을 반복하지 않고 실제 상태를 다시 읽습니다. 낮은 epoch의 명령을 거부합니다(§8.6).

**공백.** 무엇을 다시 읽어야 하는지가 Executor의 기억에만 있습니다. 또 epoch는 플랫폼 DB 안의 숫자라서, PgBouncer, DB 카탈로그, Edge API 같은 바깥 자원은 옛 Executor의 늦게 도착한 명령을 거부하지 못합니다.

**제안.** 바깥 변경 하나하나를 효과 행으로 먼저 저장합니다(PREPARED → IN_FLIGHT → 확인). 출처는 2026-11-02 팀원 메모("설계 추가 제안" 2절, https://app.notion.com/p/40c8bee9ada48029a376dea2d411db1a)입니다. 계약은 `platform/executor/README.md`의 "효과 원장" 절입니다.
- **P0에는 자동 인계가 없습니다.** 미해결 효과가 남은 채 Executor가 다시 뜨면 관찰 전용 모드로 뜹니다. 이 모드는 읽기 전용 자격(DB 역할 `executor_observe`, PgBouncer `stats_users`)만 씁니다. 계획은 SAFE_HOLD이고, 사람이 런북 `docs/runbooks/safe-hold.md`로 해소합니다.
- Executor는 StatefulSet, replicas 1입니다. 런북은 이 Pod의 강제 삭제를 금지합니다.
- 실행은 첫 효과 전에 충돌하는 자원 집합을 `resource_locks`에 한 번에 예약합니다. 효과 키에는 `run_id`와 방향 · 시도가 들어갑니다. 독립된 바깥 호출마다 행이 하나이고, 보상 효과는 `compensates`로 원효과를 가리킵니다.
- DB 효과는 자원 쪽에서 펜싱합니다. 출발지와 목적지 DB에 `bravo_fence(epoch)`를 두고, 모든 제어 트랜잭션이 먼저 `UPDATE bravo_fence SET epoch = $e WHERE epoch <= $e`를 실행합니다. 0행이면 버립니다.
- PgBouncer 관리 효과는 자원 쪽 펜스가 없습니다. `SHOW CLIENTS`에 옛 Executor의 관리 연결이 없을 때만 해소합니다. 아니면 `UNKNOWN`, SAFE_HOLD입니다. Edge API 호출은 되돌릴 수 없어 사람이 확인하기 전까지 `UNKNOWN`입니다.

**메모 원안과 다른 점.** 메모의 복구 실행권을 이용한 자동 인계는 P1로 내렸습니다. 원격 명령이 끝났음을 자원 쪽에서 증명하지 못하는 경우가 남기 때문입니다.

**늘어나는 것.** 플랫폼 DB 표 둘(`effects`, `resource_locks`), 고객 DB마다 `bravo_fence` 표 하나, 관찰 전용 자격 둘, Executor StatefulSet, 런북 `safe-hold.md`, 계약 시험 여섯 개(E1–E6). EC2 `StopInstances` 권한은 P0에 넣지 않습니다. 노드는 런북에서 사람이 멈춥니다.

**우선.** P0는 효과 표, 자원 잠금, `bravo_fence`, 자동 인계 없음, E1–E6입니다. 더 강한 증거를 갖춘 자동 인계는 P1입니다.

## D-20. 이전 건과 따로 사는 보안 보류와 별도 해제 승인

**스펙.** 게이트는 통제가 다르거나 UNKNOWN이면 그 이전을 차단합니다(§8.5). 승인은 단계별로 결속됩니다(§8.9).

**공백.** 계획을 취소하고 새로 만들거나 새 승인을 받으면, 앞서 드러난 보안 문제가 더는 막지 않습니다.

**제안.** 이전 건과 따로 사는 보류를 둡니다. 보류는 정해진 동작(배포, 경로 전환, writer 변경)을 막고, 일반 승인이나 리허설 성공으로 풀리지 않습니다. 해제는 요청, 독립 재시험, 다른 사람의 해제 승인, revision 재확인을 거칩니다. 검토 기한이 지나도 저절로 풀리지 않습니다. 출처는 같은 메모 3절입니다. 설계는 `docs/architecture/04-governance.md` 5절입니다.
- P0 보류의 범위는 앱 전체(테넌트 + 앱)입니다.
- (테넌트, 앱)마다 guard 행 하나를 둡니다. 보류 생성 · 수정 · 해제, 통제 실패 등록, 효과의 `IN_FLIGHT` 전이가 모두 이 행을 `FOR UPDATE`로 잠급니다. `IN_FLIGHT` commit이 발행 시점입니다.
- 집행 지점은 상태 머신 전이, Executor 효과, 배포 커밋과 runner, Edge 가중치, 런북 동작입니다.
- 관측, 감사, 관찰 전용 조정, 같은 실행이 만든 제한만의 ABORT_PRE_WRITE 복원은 막지 않습니다. 복원이 보류의 보안 회수를 되돌리게 되거나 상태가 불명확하면 SAFE_HOLD입니다.
- FAILBACK은 허용합니다. 다만 출발지를 덮는 활성 보류에 `writer_change`가 있으면 SAFE_HOLD에서 사람이 판단합니다.

**범위.** P0에는 보류 표, guard 행, 집행 지점의 검사, 콘솔 표시, `security_approver`의 최소 해제 양식(한 화면, 같은 검사)을 넣습니다. 자동 보류와 알림은 P1입니다.

4. 보안 동등성은 배포판이 같아서가 아니라 같은 질문의 시험 결과로 증명합니다(§8.5). 출발지와 목적지의 배포판이 달라도 게이트 규칙은 그대로입니다.

| T2 | 온프렘 목적지를 K3s로 세웁니다. Lima VM 2대(server 1, agent 1). K3s 바이너리는 판과 SHA-256으로 고정합니다. CIS 하드닝 설정은 비밀 암호화, PSA 설정 파일, 감사 정책, `protect-kernel-defaults`와 sysctl입니다. 완료 기준은 "새 VM에서 K3s가 하드닝 설정으로 뜨고 kube-bench(K3s 벤치마크) 결과가 나온다"입니다 |

## D-22. SeaweedFS를 빼고 객체 저장을 "같은 S3 계약 + 환경별 엔진"으로

**상태.** 류지환 결정(2026-11-02): SeaweedFS를 빼고, 객체 저장은 "같은 S3 계약 + 환경별 엔진"으로 둡니다. 온프렘 엔진은 Rook-Ceph RGW, EKS는 Amazon S3, GKE는 Cloud Storage입니다. 온프렘 RGW는 11/3에 실측하고, 아래 실측 항목이 실패하면 다시 정합니다. 온프렘 블록 저장은 아직 정하지 않았습니다(임시로 K3s 기본 local-path).

**스펙.** 스펙은 목적지 객체 저장을 SeaweedFS로 둡니다.
- FR-3: 목적지 기준에 SeaweedFS가 있습니다. FR-4: S3 정책을 "SeaweedFS 정책"으로 옮기는 번역안을 냅니다.
- §6 S1 기본 흐름 2(SeaweedFS를 세움), S2 기본 흐름(목적지 프로필의 시험용 SeaweedFS 버킷, SeaweedFS 버킷 정책 작성).
- §7.2 온프렘 구성, §7.3 첨부파일 행("SeaweedFS (S3 호환)")과 권한 행("OpenBao · SeaweedFS 정책").
- §8.3 제안서 예시의 `target.type`(`seaweedfs_bucket_policy`), §8.4 목적지 프로필.
- §8.8 `object_store/onprem/`(SeaweedFS).
- §9 위험 표: SeaweedFS가 무인증 거부 · 버킷 권한 시험을 지원하지 않으면 MinIO 마지막 판 고정.
- §12: SeaweedFS 채택 확정은 보안 통제 · 게이트 담당.
- T9: "OpenBao · ESO · SeaweedFS".

블록 저장(TopoLVM)은 스펙에 없고 구현 선택이었습니다(`docs/architecture/09-cni-csi.md`). 첫 후보 Rook-Ceph가 블록도 함께 맡으므로 같은 검증에서 봅니다.

**정한 것.** SeaweedFS는 쓰지 않습니다. 재단 없는 단일 프로젝트라 채택 근거를 말하기 어렵기 때문입니다(TECH-STACK-SPEC 0절).

**요구(후보를 고르는 기준).** 아래는 이 설계가 이미 기대는 것입니다.

| 요구 | 왜 |
|---|---|
| S3 API(PUT, GET, HEAD, LIST) | 앱과 첨부 복사 Job이 S3 API만 씀(D-04) |
| 버킷 정책: 익명 거부, 앱 역할만 읽기 · 쓰기 | 게이트 1차 BLOCK과 S2 번역의 대상(§6 S2, T19) |
| 버킷 하나에 묶인 자격 | 첨부 복사 Job과 리허설 시험 버킷의 최소 권한(D-04, D-12) |
| 종단 TLS | 링크 위 ENC-01(`docs/architecture/02-network.md` O10) |
| arm64, K3s 위 Lima VM 2대에 들어가는 자원 | 온프렘 데모 장비(`docs/architecture/01-environments.md` 3절) |
| GKE · EKS 목적지에도 같은 구성 | 랜딩 존(D-23) |
| 채택 근거와 라이선스 | TECH-STACK-SPEC 0절 |

**후보.**

| 후보 | 비교에서 볼 점 |
|---|---|
| Rook-Ceph RGW(객체) + RBD(블록) | 첫 후보. Rook은 CNCF 졸업 프로젝트. 객체와 블록을 한 시스템이 맡음. RGW는 S3 버킷 정책 언어의 일부를 지원(Ceph 문서). 무거움(OSD 기본 메모리 목표 4 GiB) |
| MinIO | 2025년 커뮤니티판 변경(TECH-STACK-SPEC 2.3절) |
| Garage | 가벼움. 버킷 정책 지원 여부는 확인 필요 |
| 클라우드 관리형 S3 · GCS | 관리형이라 운영 부담이 없음. 다만 D-23은 관리형을 출발지로만 다룸. 이 장단을 함께 봄 |

**첫 후보(Rook-Ceph)로 실측할 때의 배치.** 정해진 것이 아니라 스파이크의 출발점입니다.
- Lima VM 2대에 mon 1, mgr 1, OSD 2(VM마다 전용 디스크 하나), RGW 1. mon이 하나라 HA가 아닙니다.
- 풀 복제 수와 `min_size`는 실측으로 정합니다. `bravo-db`는 CNPG가 따로 복제하므로 복제 1 풀도 봅니다.
- `osd_memory_target`을 낮추고 VM 메모리를 늘립니다(`docs/architecture/01-environments.md` 3절).
- agent VM의 `pool=rehearsal:NoSchedule` taint에 맞춰 OSD와 CSI Pod에 toleration을 줍니다.
- 첨부 버킷과 버킷 전용 사용자는 ObjectBucketClaim으로 만듭니다(확인 필요).
- RGW는 TLS 포트(`securePort`)와 인증서 Secret으로 종단 TLS를 엽니다. 링크 `dst-s3`의 포트는 443으로 둡니다(확인 필요).

**검증 순서.**
1. 요구 표를 확정합니다(위 표가 초안).
2. 후보를 같은 표로 비교합니다.
3. K3s(Lima)에서 첫 후보를 띄워 버킷 정책 시험(익명 거부, 앱 역할 읽기)과 자원 사용을 잽니다.
4. 팀이 확인합니다. 정해지면 이 절의 상태를 바꾸고 T2 · T9를 고칩니다.

**어느 후보든 바뀌는 작업.** T9(객체 저장, 버킷 정책, 앱 전용 자격, 무인증 거부 시험), T3 · T15(리허설 시험 버킷과 NetworkPolicy 허용 대상, D-12), T11(제안서 `target.type`), T14 · T19(S3 통제 시험의 대상), D-04(첨부 복사 Job의 대상과 링크 `dst-s3` 포트). Rook-Ceph로 정하면 T2에 Rook operator, Ceph 클러스터, RBD StorageClass `bravo-db` · `bravo-general`이 더해집니다.

**비용.** 온프렘은 팀원 Mac의 Lima VM이라 클라우드 비용이 없습니다. Rook-Ceph면 Mac 자원을 더 씁니다(VM 메모리 합 약 28 GiB, 전용 디스크 약 100 GiB, 추정).

**남는 위험.** 스펙 §9의 "실패하면 MinIO" 대안을 그대로 둘지는 후보 비교에서 정합니다. 정하기 전까지 S2의 버킷 정책 장면은 대상 저장소가 없어 멈춥니다. 11/3 스파이크가 가장 먼저입니다.

**스펙 v0.2.** 정해지면 FR-3, FR-4, §6 S1 · S2, §7.2, §7.3, §8.3 예시, §8.4, §8.8, §9, §12, T9의 문구를 바꿉니다.

**리서치 결과와 권고(2026-11-02, `research/platform-research/object-storage-cdn-2026-11-02.md`).** 멀티 클라우드 서비스가 객체 저장소와 CDN을 다루는 방식을 공식 자료로 조사했습니다. 권고는 "같은 계약, 환경별 엔진"입니다. 아직 제안이며, 원칙 해석은 팀장 확인이 필요합니다.

| 환경 | 엔진 | 근거 |
|---|---|---|
| 온프렘 K3s | S3 호환 자체 저장소. 후보 Rook-Ceph RGW(11/3 실측) | 온프렘에는 관리형이 없음. Red Hat ODF도 RGW를 온프렘 객체 저장으로 둠 |
| EKS 목적지 | Amazon S3 | 클라우드 위에 Ceph를 올리면 EBS 복제 위에 다시 복제하고, 초보 고객이 클라우드마다 Ceph를 운영하게 됨(안티패턴) |
| GKE 목적지 | Cloud Storage(XML API, HMAC 키) | GKE Autopilot은 Rook-Ceph에 필요한 특권 · hostPath를 기본으로 막음 |

- **같은 것(계약).** 앱 매니페스트, 환경 변수 이름, 버킷 이름, 자격 Secret 이름, 통제 질문 ID가 세 환경에서 같습니다. 다른 것은 랜딩 존 overlay의 엔드포인트와 자격 출처뿐입니다(D-23의 블록 저장과 같은 원리).
- **게이트는 정책 문서가 아니라 행동을 시험합니다.** OBJ-01 서명 없는 GET 거부, OBJ-02 서명 없는 LIST 거부, OBJ-03 서명 없는 PUT 거부, OBJ-04 앱 자격 읽기 · 쓰기 허용(대조군), OBJ-05 다른 자격 거부, OBJ-06 평문 HTTP 거부. 고정 키의 시험 객체를 두어 404로 거짓 통과하지 않게 합니다. 각 환경의 공개 차단 설정은 보조 근거입니다.
- **S2 제안서의 `target.type`**은 온프렘이면 `rgw_bucket_policy`, GKE면 `gcs_iam_policy`, EKS면 `s3_bucket_policy`입니다.
- **CDN.** 첨부는 캐시하지 않습니다(`Cache-Control: private, no-store`, Cloudflare 캐시 우회 규칙). 저장소 전환은 지금처럼 DB의 `active_store`와 Cloudflare LB의 앱 전환이 맡습니다.
- **읽을 때 옮기기(Sippy 방식)는 쓰지 않습니다.** 온프렘에 AWS 자격이 필요하고, 컷오버 전 전체 대조를 증명할 수 없기 때문입니다. 순서는 D-04 그대로입니다(대량 복사, 차이분, 쓰기 전환, 대조, 읽기 전환, 옛 저장소 보존).
- **앱 설정.** `AWS_REQUEST_CHECKSUM_CALCULATION`, `AWS_RESPONSE_CHECKSUM_VALIDATION`을 `when_required`로 둡니다. AWS SDK의 새 체크섬 기본값이 S3 호환 저장소와 맞지 않을 수 있습니다.
- **고르지 않은 것.** Cloudflare R2(S3 API로 버킷 정책 · 공개 차단 · Object Lock을 다 지원하지 않고, 데이터 위치 보장에 일본이 없음), MinIO(`minio/minio` 저장소가 2026-04 보관 상태, 무료판은 단일 노드 약관), Garage(버킷 정책 없음). 그래서 스펙 §9의 "MinIO 마지막 판 고정" 대안은 지웁니다.
- **폴백.** 팀장이 D-23을 "엔진까지 같음"으로 정하면 모든 목적지에 RGW를 둡니다. 데모에서는 EKS · GKE 목적지를 만들지 않으므로 비용은 늘지 않지만, 위 한계를 발표에 밝힙니다.
- **11/3 실측 항목(Rook-Ceph).** RGW region 값과 path-style 동작, ObjectBucketClaim의 버킷 정책과 공개 차단을 함께 거는지, RGW의 SSE-KMS가 금고(OpenBao · Vault)와 동작하는지, Lima VM 자원에 들어가는지.

## D-23. 온프렘 · GKE · EKS에 같은 랜딩 존

**스펙.** 스펙은 목적지를 온프렘 하나로 둡니다(§7.2). 출발지 관리형 서비스의 대응은 §7.3 표에 있고, 그 표는 AWS에서 온프렘으로 가는 한 방향입니다. 고객 클러스터마다 무엇을 설치하는지 정한 공통 묶음은 없습니다. §8.8은 환경별 모듈 구현만 적습니다. §4는 설계가 목적지와 무관하다고 적습니다.

**결정.** 팀장(류지환)이 2026-11-02에 정했습니다. 플랫폼이 만드는 모든 고객 클러스터(온프렘 K3s, GKE, EKS)에 같은 묶음(랜딩 존)을 같은 판, 같은 이름, 같은 정책으로 설치합니다. 설계는 `docs/architecture/11-landing-zone.md`, 클러스터 지도는 `docs/architecture/10-cluster-overview.md`입니다.

| 묶음 | 구성 |
|---|---|
| 데이터베이스 | CNPG + PgBouncer |
| 객체 · 블록 저장 | 모든 목적지에 같은 S3 호환 저장소와 블록 저장. 후보 Rook-Ceph RGW + RBD(제안 D-22, 검증 중). StorageClass `bravo-db`, `bravo-general` |
| 비밀 | Vault 계열 금고(OpenBao 또는 Vault, 열림) + External Secrets |
| 정책 | Kyverno |
| 배포 | Argo CD |
| 연결 | `cf-edge` + `bravo-link`(D-16) |
| 관측 | OTel Collector 에이전트 |

- 앱은 표준 인터페이스(PostgreSQL, S3 API, 쿠버네티스 Secret, OTLP)만 씁니다.
- 클라우드 차이는 얇은 공급자 overlay(`k3s`, `eks`, `gke`) 한 층에만 둡니다. 저장 장치의 바탕, 노드 배치, 플랫폼 구성요소의 클라우드 자격입니다. 묶음은 `deploy/landing-zone/`의 base 하나와 overlay 셋입니다.
- 클라우드 관리형 S3, GCS, Secrets Manager, RDS는 목적지 구성요소로 쓰지 않습니다. 첫 이전 때 번역할 출발지로만 다룹니다.

**이유.**
1. 랜딩 존끼리는 모양이 같습니다. 그래서 컷오버 엔진, 첨부 복사(같은 저장소에서 같은 저장소로), 비밀 이전이 방향과 상관없이 같습니다. 첫 이전 뒤에는 번역 없이 어디로든 다시 옮깁니다. 출구전략 제품의 주장이 이것입니다.
2. 고객 경험이 같습니다. 입력은 대상 종류, 이름, 지역, 크기뿐입니다(D-21의 제품 원칙).
3. 빈칸이 한 번에 채워집니다. GKE 객체 저장이 열려 있던 것, 비밀 저장이 클라우드마다 갈라질 수 있던 것, 고객 클러스터의 관측 경로가 없던 것입니다(`11-landing-zone.md` 6절).

**스펙과 다른 점.**
- §7.3 표는 "첫 이전 때의 번역표"가 됩니다. 랜딩 존 사이의 이동에는 번역이 없습니다.
- 데모 출발지(`source-aws`)는 바뀌지 않습니다. 앱이 S3, Secrets Manager, KMS를 직접 부르는 상태가 S2의 재료이기 때문입니다(§8.10).
- 고객 클러스터에 OTel Collector 에이전트가 늡니다. Argo CD는 D-16에서 이미 제안했습니다.

**작업별 영향.**

| 작업 | 바뀌는 것 |
|---|---|
| T2, T9 | 온프렘에 랜딩 존 전체를 먼저 세웁니다(11/3부터, Lima). 객체 저장과 비밀이 base의 일부가 됩니다 |
| T6 | 바뀌지 않습니다. 데모 출발지는 클라우드 고유 환경으로 둡니다 |
| T18 | 고객 클러스터의 OTel Collector 에이전트가 링크로 플랫폼 Collector에 보냅니다. 담당은 회의에서 정합니다 |
| D-01 | GKE 목적지도 같은 랜딩 존입니다. 객체 저장은 온프렘과 같은 저장소입니다(후보 RGW면 OSD를 PD PVC 위에) |
| 환경 생성 | 상태 머신 REQUESTED, PROVISIONING, BOOTSTRAPPING, VERIFYING, READY(`11-landing-zone.md` 4절). 운영자 MCP의 `env_create` 제안(`docs/architecture/08-operator-mcp.md` 4절) |

**늘어나는 것.** `deploy/landing-zone/` base와 overlay 셋, 클라우드 위 객체 저장소(후보 Rook-Ceph면 OSD를 PVC 위에), 고객 클러스터의 OTel Collector 에이전트, 환경 생성 상태 머신.

**줄어드는 것.** 목적지별 저장 · 비밀 구성의 갈래(S3, GCS, Secret Manager), 방향마다 따로 하는 이전 설계.

**비용.** 클라우드 목적지에 자체 객체 저장소(후보 Rook-Ceph)를 올리면 PVC와 노드 자원이 늡니다. 데모에서 EKS · GKE 목적지는 검증만 하고 만들지 않습니다(`11-landing-zone.md` 8절). 그래서 데모 비용은 늘지 않습니다.

**남는 차이.** 노드 OS가 다릅니다. 온프렘 K3s는 server 1대라 HA가 아닙니다. 클라우드 위 자체 객체 저장소는 관리형 객체 저장보다 운영 부담이 큽니다(`11-landing-zone.md` 7절). 이 장단은 D-22의 후보 비교에서 함께 봅니다.

**상태.** 류지환 결정(2026-11-02), 회의 공유.

**해석(팀장 결정 2026-11-02, 1급 원천 「기술 스택(툴) 조합」과 맞춤).** "같은 구조"는 "같은 계약 · 같은 경험"을 뜻합니다. 앱 매니페스트, 이름, 통제 시험, 화면, 진행 단계가 같고, 엔진은 환경에 맞게 고를 수 있습니다(예: 객체 저장은 온프렘 RGW, EKS S3, GKE Cloud Storage. D-22). 원천의 "모든 환경에 같은 도구를 설치하는 것은 목표가 아님"과 같은 원칙입니다.

## D-25. 전체 상태 경로의 구현 선택

2026-11-02 상태 머신에 ANALYZE, PROPOSE, REHEARSE, NEEDS_HUMAN, DONE, FAILBACK, DONE_ROLLED_BACK을 넣으며 스펙이 정하지 않은 다섯 가지를 골랐습니다. 회의에서 정합니다.

| 선택 | 구현 | 이유 |
|---|---|---|
| ANALYZE 분기 | 수집기 인벤토리에 `code_change` 또는 `unclassified` 의존성이 있으면 PROPOSE, 없으면 GATE. 통제 차이는 게이트 BLOCK 이유로 남김 | S1이 게이트 1차 BLOCK을 S2의 계기로 둠. 수집기가 없으면 `inventory.status=unconfigured`를 그대로 기록 |
| 재제안 | GATE BLOCK 뒤 운영자가 `rehearsals`를 부르면 GATE → PROPOSE. 사람이 직접 고치고 게이트를 다시 돌리는 파일럿 경로도 남김 | 두 경로 모두 스펙 S1 · S2와 맞음 |
| WATCH 재시험 | WATCH에서 `gate`를 부르면 통제만 같은 규칙으로 판정. PASS면 DONE, BLOCK이면 WATCH에 남고 새 되돌리기 승인 요청을 냄 | §8.2 "재시험 PASS". 복제 준비 값은 되돌리기 쪽 판단이라 뺌 |
| NEEDS_HUMAN 재개 | 콘솔의 운영자만 시도 수를 0으로 되돌리고 PROPOSE로 재개. MCP는 거부(`needs_human_console_only`) | 상한을 AI 채널이 우회하지 못하게 함 |
| 도구 이름 | §8.3의 `plan.propose` 등을 `plan_propose`처럼 밑줄로 | 모델 도구 이름에 점을 쓸 수 없음 |
| 역할 | 단계별 허용 역할(ANALYZE: discovery, db, governance / PROPOSE · REHEARSE: governance, app_migration, ci). 도구 계층은 역할별 허용 목록 YAML(`platform/agent/allowlists/`)을 읽고 없으면 모두 거부 | 2026-11-02 조정 메모 |

## D-24. 관리형 PostgreSQL 끝점과 PgBouncer 끼워 넣기

**스펙.** 컷오버는 논리 복제, PgBouncer PAUSE/RESUME, 펜싱, barrier로 합니다(FR-9, §8.6). 영수증의 출발지와 목적지는 CNPG입니다(§8.6 영수증 예시). 데모 앱은 PostgreSQL 16 이상, 모든 테이블 PK, 앱 전용 역할을 지킵니다(§8.10). 관리형 DB(RDS 등)를 출발지 끝점으로 받는 절차, 그 앞에 PgBouncer를 넣는 절차는 없습니다. D-23은 관리형 RDS를 목적지 구성요소로 쓰지 않고 첫 이전의 출발지로만 다룹니다.

**제안.** 설계는 `docs/architecture/12-db-migration-matrix.md`입니다.
1. **끝점.** RDS for PostgreSQL, Aurora PostgreSQL, Cloud SQL for PostgreSQL을 출발지 끝점으로 받습니다. 고객이 원하면 목적지 DB 백엔드로도 씁니다. 랜딩 존의 기본은 CNPG 그대로입니다. AlloyDB는 직접 연결에서 verify-full을 쓸 수 없어 보류합니다(공식 문서).
2. **엔진은 하나.** 아홉 방향 모두 native 논리 복제, 우리 PgBouncer, `bravo_fence` 펜싱, 같은 영수증입니다. 클라우드 이전 서비스(AWS DMS, Google DMS)는 native가 막힌 정방향에만 쓰고, 그때 계획은 NEEDS_HUMAN입니다. 되돌리기 경로가 없기 때문입니다.
3. **온보딩 두 단계.** 컷오버와 따로, 고객 정비 시간에 합니다.
   - 논리 디코딩 켜기: RDS · Aurora 파라미터 그룹, Cloud SQL 플래그. 재시작이 필요합니다(공식 문서). Executor는 클라우드 자격이 없으므로 위임된 IaC 실행기나 고객이 합니다. `change` 승인이 필요합니다.
   - PgBouncer 끼워 넣기: 관리형 DB에는 우리가 쓸 PAUSE가 없습니다(RDS Proxy 공식 문서). 같은 VPC의 고객 클러스터에 랜딩 존과 같은 PgBouncer를 두고 앱 주소를 바꿉니다. 사전 조사, 지연 측정, 직접 연결 0 확인을 거칩니다(문서 5.2절).
4. **TLS.** 관리형 인증서에는 우리 링크 이름이 없습니다. 클라이언트는 공급자 이름으로 검증하고 TCP만 링크로 보냅니다(libpq `host` + `hostaddr`, PgBouncer는 Pod `hostAliases`). 관리형 구독자가 우리 publisher를 검증하는 방법은 아직 확인 전입니다(문서 6절, SPK-03).
5. **펜싱 권한.** `executor_ctl`은 superuser가 아닙니다. PG16 규칙에 맞춰 앱 역할의 ADMIN OPTION과 `pg_signal_backend`를 온보딩에서 받습니다.

**이유.**
1. AWS 고객 대부분은 RDS · Aurora를 씁니다(`TECH-STACK-SPEC.md` 3절 2번). 출발지 RDS를 못 받으면 첫 이전이 막힙니다.
2. 고객이 관리형 DB를 원해도 앱 경험(같은 PgBouncer 주소, 같은 Secret 이름)과 컷오버 엔진이 같게 유지됩니다.
3. 엔진이 하나라 영수증, 효과 원장, 되돌리기 규칙이 방향과 상관없이 같습니다.

**스펙과 다른 점.**
- 영수증의 `source`, `target`에 관리형 끝점이 올 수 있습니다. 형식은 같습니다.
- 관리형에는 `pg_hba`가 없습니다. 평문 거부는 RDS `rds.force_ssl`, Cloud SQL SSL 모드로 대신합니다.
- 관리형 구독자의 CA 검증이 안 되면 `sslmode=require` + `channel_binding=require`를 ENC-01 예외로 두는 안이 남습니다. 보안 검토가 필요합니다.
- Cloud SQL HA 인스턴스는 구독자가 될 수 없습니다(공식 문서). HA 출발지는 HA를 끄는 동의가 없으면 데이터째 되돌리기(FR-11)를 약속하지 않습니다.
- D-23의 "관리형 RDS를 목적지로 쓰지 않음"에 DB만 예외를 둡니다. 팀장 결정이 필요합니다.

**작업별 영향.**

| 작업 | 바뀌는 것 |
|---|---|
| T12, T13 | 관리형 끝점에서도 같은 단계. 해시 규칙 v1에 `COLLATE "C"` 정렬과 세션 설정 고정을 더하자는 제안 |
| T8 | 관리형 끝마다 N6, N11을 같은 방식으로 |
| 인프라 · CI | `infra/modules/database/`에 `rds`, `cloudsql` 구현(제안). 링크 내부 LB |
| 보안 통제 · 게이트 | 관리형 구독자의 CA 방식, ENC-01 예외 여부 |

**늘어나는 것.** 온보딩 두 단계, 관리형 DB 모듈 둘, 링크 내부 LB, 스파이크 시험 SPK-01–SPK-11.

**비용.** 관리형 인스턴스, 저장소, 백업, HA, 내부 LB 요금이 듭니다. 금액은 채택할 때 확인합니다. 데모에서는 비용 승인 전에 관리형 목적지를 만들지 않습니다.

**남는 위험.** 관리형 구독자의 CA와 경로(SPK-03), Aurora writer 장애 조치 때 논리 슬롯(SPK-08), RDS의 `max_slot_wal_keep_size`(SPK-01)가 확인 전입니다. 관리형 구독자용 공개 CA 인증서 안을 채택하면 cert-manager(ACME)가 늘어 `02-network.md` 12절이 바뀝니다. PgBouncer 끼워 넣기는 출발지 앱이 같은 VPC의 쿠버네티스에 있을 때만 됩니다. 슬롯이 고객 운영 DB의 저장 공간을 채우지 않게 경보와 사람의 슬롯 삭제 절차를 둡니다.

**상태.** 제안(2026-11-02). 스파이크 결과를 붙여 회의에서 정합니다.

## D-26. 키와 비밀은 플랫폼 금고 하나만 보관

**결정.** 류지환 결정(2026-11-02): "키 관리는 모두 우리 플랫폼이 맡는거야. 다른 쪽이 가면 안돼."

**스펙.** 비밀은 목적지마다 OpenBao + External Secrets입니다(§7.2, §7.3). 서비스 토큰 · 터널 토큰의 보관 위치는 정하지 않았습니다.

**바뀌는 것.**

| 항목 | 전 | 후 |
|---|---|---|
| 보관 주체 | 목적지 클러스터마다 OpenBao | 플랫폼 OpenBao 하나. 오늘 파일럿은 플랫폼 Compose |
| 고객 클러스터 | OpenBao + ESO | ESO만. 링크를 거쳐 플랫폼 OpenBao에서 그 환경 경로의 값만 당겨 옴 |
| Cloudflare API 토큰 | 미정(노트북 `.env`) | 플랫폼 OpenBao. `.env`는 첫 부트스트랩에만 쓰고 바로 옮긴 뒤 지움 |
| 터널 토큰 · Access 서비스 토큰 | 부트스트랩 스크립트가 Secrets Manager에 씀 | 플랫폼 키 단계가 Cloudflare API에서 받아 OpenBao에 바로 씀. 파일 · 상태에 남기지 않음 |
| Terraform | 비밀이 상태에 들어갈 수 있음 | 상태와 출력에 비밀 값 없음. 터널 비밀은 Cloudflare가 만들고, 토큰은 Terraform이 읽지 않음 |
| CI | 미정 | 저장소 비밀 없음. OIDC만 |
| 에이전트 · Harbor 샌드박스 | 도구 계층이 막음 | 같음. 샌드박스와 프롬프트에는 비밀 값을 주지 않음 |

**예외.** 출발지 AWS 앱의 Secrets Manager 비밀은 고객의 기존 상태입니다. 플랫폼 키가 아니고, 이전 때 플랫폼 금고로 옮길 대상입니다(S2 장면).

**열림.** 저장 데이터 암호화의 루트 키(클라우드 KMS CMK)까지 플랫폼이 쥘지 정하지 않았습니다. 후보는 가져온 키 재료(BYOK)나 외부 키 저장소(XKS)입니다.

## D-27. 역할별 에이전트 여섯과 구조화 출력 채널

**스펙.** 에이전트 워커 하나가 의존성 분류, 번역 · 수정 제안서, 실패 원인 추정, 승인 요약, 사후 리포트를 맡습니다. CI 에이전트는 따로 두지 않습니다(§8.3). 제안서는 `plan.propose` 도구로 냅니다.

**바뀌는 것.** 류지환 지시(2026-11-02)로 역할을 여섯으로 나눕니다: Discovery, DB, Governance, App Migration, CI, Report. 역할마다 허용 목록(도구, 샌드박스 작업, 검사 argv, 바이너리, 상태), 샌드박스 이미지, Harbor task가 따로 있습니다. 모델의 결과 채널은 SDK 구조화 출력이고, 워커가 Pydantic으로 검증한 뒤 `plan_propose`로 냅니다. 모델에게는 제출 도구가 없습니다. 설계는 `docs/architecture/13-agents.md`입니다.

**지키는 것.** 제안만 하고 판정 · 실행은 코드가 합니다. 실행 구간과 게이트에는 에이전트가 없습니다. 재시도 상한 3회, NEEDS_HUMAN, NFR-4 · NFR-5는 그대로입니다. CI 에이전트는 push · 서명 · 배포 권한이 없습니다.

**상태.** 설계안과 코드(`platform/agent/`). 회의에서 공유합니다. 도구 계층의 허용 목록 로더와 제안서 검사가 이 형식을 읽도록 바꾸는 일이 남았습니다(13 9절 연결 메모).
