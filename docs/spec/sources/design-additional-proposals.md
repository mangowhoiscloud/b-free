## 2. 미해결 외부 효과의 실행 통제

> 그림: `01-unresolved-effects.png` (Notion 첨부)

**반영 위치: 8.2 상태 머신, 8.6 Executor 계약**

### 2.1 기존 설계와의 차이

기존의 “응답 유실 시 실제 상태를 다시 읽는다”는 원칙을 유지한다.

추가 제안은 **무엇을 재조회해야 하는지 영속적으로 보존하고, 그 결과가 확정되기 전까지 충돌하는 변경을 막는 계약**이다.

### 2.2 효과 단위 기록

업무 상태와 별도로 개별 외부 변경을 기록한다.

예를 들어 하나의 `CUTOVER` 작업 안에서도 다음 효과를 구분한다.

- 출발지 Pooler 정지
- 출발지 writer 권한 제한
- 목적지 writer 활성화
- Pooler 접속 대상 변경
- Edge 경로 변경

| 필드 | 내용 |
| --- | --- |
| 범위 | 조직·앱·환경·실제 자원 식별자 |
| 의도 | 계획 digest·단계 ID·동작·입력 digest |
| 실행권 | 작업 ID·owner·epoch·만료 |
| 중복 방지 | 범위에 결합된 멱등 키 |
| 결과 | 효과 상태·관측 시각·근거 참조 |
| 복구 | 미해결 사유·조정 작업·최종 판정 |

접속 비밀은 값 대신 등록된 참조로 기록한다.

### 2.3 효과 상태

| 상태 | 의미 |
| --- | --- |
| `PREPARED` | 변경 의도를 저장했으나 호출 여부가 아직 확정되지 않음 |
| `IN_FLIGHT` | 외부 호출을 시작함 |
| `CONFIRMED_APPLIED` | 의도한 변경의 적용을 확인함 |
| `CONFIRMED_NOT_APPLIED` | 변경이 적용되지 않았고 늦게 적용될 가능성도 해소됐음을 확인함 |
| `UNKNOWN` | 적용 여부 또는 지연 실행 가능성을 확정할 수 없음 |

**타임아웃이나 현재 값이 원래 값과 같다는 사실만으로 `CONFIRMED_NOT_APPLIED`를 부여하지 않는다.** 이전 요청이 나중에 적용될 수 있기 때문이다.

### 2.4 실행·복구 규칙

1. 외부 호출 전에 변경 의도를 저장한다.
2. 현재 실행권과 허가를 확인하고 `IN_FLIGHT`를 확정한다.
3. DB 행 잠금을 해제한 뒤 외부 요청을 보낸다.
4. 응답과 실제 자원 상태를 관측해 결과를 기록한다.
5. 응답 유실 시 `UNKNOWN`을 보존하고 자동 재호출하지 않는다.
6. 미해결 효과가 남아 있으면 동일 앱·자원에 충돌하는 일반 변경의 실행권 인계를 차단한다.
7. 복구 실행권은 조회·조정용으로 제한한다.
8. 이전 실행자와 지연된 명령의 영향이 해소된 뒤 일반 실행을 재개한다.

제어 DB의 epoch와 외부 자원의 fencing은 구분한다. 외부 Executor가 epoch를 검사하지 않는다면, 제어면의 숫자 증가만으로 오래된 요청을 막았다고 판단하지 않는다.

### 2.5 장애별 처리

| 상황 | 처리 |
| --- | --- |
| 외부 적용 직후 응답 유실 | 원장 보존 후 실제 효과 조회 |
| 워커 종료 후 리스 만료 | 미해결 효과가 있으면 일반 인계 차단 |
| 이전 epoch의 명령 지연 도착 | 실행 경계에서 거부하거나 요청 종결을 확인 |
| 승인 취소 후 기존 호출의 응답 도착 | 관측은 보존하되 새 변경·다음 단계 진행은 별도 검사 |
| 조정 근거 부족 | `UNKNOWN` 또는 `SAFE_HOLD` 유지 |

### 2.6 인수 기준

- 변경 적용 직후 워커를 종료해도 재시작한 워커가 같은 변경을 반복하지 않는다.
- 미해결 효과가 남아 있는 상태에서 다른 실행자의 충돌 작업이 차단된다.
- 리스 만료만으로 미해결 상태가 제거되지 않는다.
- 조회 전용 복구 권한으로 새로운 변경을 수행할 수 없다.
- 오래된 명령의 지연 도착을 포함한 장애 시험을 통과한다.

## 3. 독립 보안 보류와 별도 해제 승인

> 그림: `02-independent-security-hold.png` (Notion 첨부)

**반영 위치: 8.2 상태 머신, 8.5 게이트, 8.9 API**

### 3.1 기존 설계와의 차이

기존 게이트는 통제 실패 시 해당 이전을 차단한다.

추가 제안은 **이전 작업이 취소되거나 새 승인이 발급돼도 유지되는 독립 보안 보류**다.

### 3.2 보류 데이터

| 필드 | 내용 |
| --- | --- |
| 보류 ID·revision | 보류의 식별자와 변경 버전 |
| 적용 범위 | 조직·앱·환경·자원 |
| 사유·근거 | 사고·정책 위반·관측 참조 |
| 제한 동작 | 배포·경로 전환·writer 변경 등 |
| 허용 대응 | 격리·권한 폐기 등 승인된 대응 |
| 해제 조건 | 필요한 수정·재검증·승인 권한 |
| 검토 기한 | 담당자 확인·에스컬레이션 기준 |

**검토 기한이 지나도 보류를 자동 해제하지 않는다.**

### 3.3 해제 절차

```text
보류 등록
→ 해제 요청
→ 지정 조건의 독립 재검증
→ 해제 권한자의 승인
→ 현재 보류 revision·새 사고 유무 재확인
→ 해제 확정
```

- 해제 요청과 승인은 서로 다른 인증된 주체가 수행하도록 한다.
- 승인 권한은 요청 본문이 아니라 서버의 조직·역할 정책으로 판단한다.
- 해제 검토 중 새로운 관련 사고나 보류 변경이 발생하면 기존 해제 판단을 재검토한다.
- 보류 상태와 revision의 확인·해제는 원자적으로 처리한다.

### 3.4 실행 중 보류 발생

- 이후의 새로운 변경은 차단한다.
- 이미 발행한 외부 효과는 조회·조정 대상으로 유지한다.
- 격리 등 긴급 대응은 사전 승인된 정확한 범위에서만 허용한다.
- 보류 등록이 관측·감사·복구 정보를 끊지 않도록 한다.
- 제어면 장애만으로 정상 서비스의 writer를 임의 전환하거나 종료하지 않는다.

### 3.5 인수 기준

- 새 배포 승인으로 기존 보류를 우회할 수 없다.
- 리허설 성공만으로 보류가 해제되지 않는다.
- 해제 승인 이후 보류 revision이 바뀌면 이전 승인으로 해제할 수 없다.
- 검토 기한 만료 시 보류가 유지되고 담당자에게 에스컬레이션된다.
- 보류 상태에서도 허용된 관측·복구와 금지된 변경이 구분된다.

## 4. 첨부파일의 실제 이전·역방향 복구

> 그림: `03-attachment-migration.png` (Notion 첨부)

**반영 위치: 8.6 데이터 이전, S3·S4 시나리오, 8.10 데모 앱**

### 4.1 기존 설계와의 차이

기존의 S3→SeaweedFS endpoint·권한 변경은 유지한다.

추가 제안은 **기존 객체와 이전 중 변경된 객체를 실제로 옮기고, DB 메타데이터와 함께 검증하는 절차**다.

### 4.2 지원 계약

첫 경로에서는 다음 조건을 권장한다.

- 첨부파일마다 논리 객체 ID를 부여한다.
- 파일 교체는 기존 객체 덮어쓰기보다 새 버전 생성으로 처리한다.
- DB는 사용 중인 객체 버전과 내용 digest를 참조한다.
- 객체 삭제는 이전·복구 보존 기간을 고려해 지연 처리한다.
- 업로드·교체·삭제 요청에는 멱등 키를 사용한다.

임의의 덮어쓰기·삭제를 허용하는 앱은 변경 포착과 충돌 처리가 검증된 경우에만 지원한다.

### 4.3 객체 이전 목록

| 필드 | 내용 |
| --- | --- |
| 논리 객체 ID | 저장소가 달라도 유지되는 업무 식별자 |
| 출발지 객체 참조 | 키·버전 또는 불변 참조 |
| 목적지 객체 참조 | 목적지의 키·버전 |
| 무결성 | 크기·전체 내용 checksum·알고리즘 |
| 업무 상태 | 준비·확정·교체·삭제 |
| 변경 순서 | 변경 기록의 위치·최종 경계 |
| 검증 결과 | 복사·내용 대조·참조 확인 |

출발지와 목적지의 버전 ID가 같아야 한다고 가정하지 않는다. **동일한 논리 객체의 내용과 업무 참조가 유지되는지** 판정한다. 객체 무결성에는 명시적인 checksum 검증을 사용한다. [AWS 객체 무결성 문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity.html)

### 4.4 DB와 객체 저장의 불일치 처리

DB와 객체 저장소 사이에 하나의 원자적 트랜잭션이 있다고 가정하지 않는다.

권장 업로드 흐름은 다음과 같다.

```text
업로드 의도·멱등 키 기록
→ 객체 저장
→ 내용 checksum 확인
→ DB 첨부 참조 확정 및 변경 이벤트 기록
→ 확정된 이벤트를 이전 작업이 처리
```

- 객체 저장 후 DB 확정 실패: 미참조 객체로 분류하고 조정한다.
- DB 확정 후 응답 유실: 같은 멱등 키로 기존 결과를 조회한다.
- 변경 이벤트 전달 실패: outbox에서 재전달한다.
- 중복 전달: 객체 버전과 작업 키로 중복 효과를 제한한다.

Outbox는 **DB 변경과 전달 의도**를 함께 저장하는 수단이다. 객체 저장까지 원자적으로 만든다고 해석하지 않는다. [Transactional Outbox 설명](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

### 4.5 최종 전환 조건

1. 초기 객체 복사와 변경분 처리를 완료한다.
2. 새 업로드를 제한하고 진행 중 작업을 배출한다.
3. 사전 발급 URL·multipart upload·worker 등 우회 쓰기 경로를 통제한다.
4. 최종 객체 변경 경계를 확정한다.
5. 최종 DB 상태가 참조하는 모든 객체의 존재·내용·접근 권한을 확인한다.
6. 미해결 업로드·삭제·복사 작업이 없음을 확인한다.
7. 목적지 신규 첨부를 되돌릴 경로를 준비한 뒤 전환한다.

진행 중 요청이 나중에 객체를 변경할 가능성이 남아 있으면 단순 대기 시간 초과로 정리가 끝났다고 판단하지 않는다.

### 4.6 복구 조건

목적지에서 새 첨부가 생성된 뒤 복귀하려면 다음을 충족해야 한다.

- 목적지 객체 쓰기 봉쇄
- 신규·교체·삭제 기록의 역방향 반영
- 최종 DB 참조와 출발지 객체의 내용 일치
- 복귀 이후 읽기·쓰기·접근 거부 확인

메시지 DB만 복구되고 첨부가 누락된 상태는 복구 완료로 처리하지 않는다.

### 4.7 인수 기준

- 업로드 도중 전환해도 확정된 첨부가 유실되지 않는다.
- 동일 요청 재전송으로 중복 업무 참조가 생성되지 않는다.
- 목적지에서 생성한 신규 첨부를 포함해 역방향 복구한다.
- 객체 누락·checksum 불일치·미해결 작업이 있으면 전환을 차단한다.
- 객체 수·용량·변경률별로 전환 예산을 실측한다.

## 5. 검증 환경의 실제 접근 통제

> 그림: `04-verifier-access-boundary.png` (Notion 첨부)

**반영 위치: 8.3 에이전트 도구, 8.4 리허설 namespace**

### 5.1 기존 설계와의 차이

별도 검증 Job·비공개 테스트는 기존 설계다.

추가 제안은 **에이전트가 사용하는 대리 실행 도구도 검증 환경에 접근하지 못하도록 하는 구체적인 권한 계약**이다.

### 5.2 실행 권한 분리

| 주체 | 허용 범위 | 금지 범위 |
| --- | --- | --- |
| 에이전트 | 작업 복사본·등록된 도구 호출 | Kubernetes 자격 증명·검증 환경 |
| 작업 실행 broker | 승인된 작업 Pod·container의 제한 실행 | 검증 Pod exec·운영 자원 변경 |
| 검증 controller | 고정 템플릿으로 verifier 생성·결과 수집 | 에이전트가 지정한 임의 실행 |
| verifier | 승인 산출물·독립 테스트·필요한 시험 대상 | 운영 비밀·서명 키 |
| 결과 수용기 | 출처·요청·산출물·검증기 결합 확인 | 성공 문자열만으로 승인 |

에이전트에게 Pod·Job·RoleBinding·ServiceAccount를 임의 생성하거나 변경하는 권한을 주지 않는다. 워크로드 생성 권한 자체가 Secret·서비스 계정 접근으로 이어질 수 있으므로 별도 검토한다. [Kubernetes RBAC 권장사항](https://kubernetes.io/docs/concepts/security/rbac-good-practices/)

### 5.3 실행 대상 결합

`rehearsal.exec` 허가는 다음 정보에 결합한다.

```text
조직 / 앱 / 작업 ID
클러스터·namespace 식별자
Pod 이름 + UID + container
허용 동작·작업 디렉터리·입력 한도
정책 revision·기한·호출 횟수
```

- 호출자가 임의의 Pod를 선택하지 못하게 한다.
- Pod 이름을 작업 사이에 재사용하지 않는다.
- 작업 Pod의 교체·삭제·UID 변경 시 이전 허가를 폐기한다.
- 작업 Pod의 생성·교체 권한은 신뢰된 controller만 가진다.
- 실제 호출 직전에 대상과 현재 허가를 다시 확인한다.

**UID 제한은 broker의 책임이다.** RBAC의 자원 이름 제한만으로 UID까지 보호했다고 판단하지 않는다. [Kubernetes RBAC 문서](https://kubernetes.io/docs/reference/access-authn-authz/rbac/)

### 5.4 검증 환경 분리

권장 기본 구성은 작업별 **실행 namespace와 검증 namespace를 분리**하는 방식이다.

- 작업 broker는 검증 namespace 권한을 갖지 않는다.
- 테스트 볼륨·검증기 설정·결과 저장 경로를 공유하지 않는다.
- 전용 artifact 전달기를 통해 허용 산출물만 전달한다.
- 검증기는 고정 이미지·테스트 기준을 사용한다.
- 더 강한 위협 모델에서는 별도 노드·클러스터·격리 backend를 검토한다.

별도 namespace 구성만으로 적대적 코드에 대한 충분한 격리를 선언하지 않는다.

### 5.5 산출물·결과 수용

산출물 전달 시 다음을 검사한다.

- 허용 경로·파일 유형·개수·총 크기
- path traversal·symlink·특수 파일
- source·patch·image digest
- 테스트·verifier 버전
- 원래 작업 요청과 실행 시도 식별자

검증 결과는 에이전트 stdout이 아니라 독립 controller가 수집한다. 결과는 인증된 발행 경로로 전달하고 다른 작업·이전 시도의 결과를 재사용하지 못하게 한다.

### 5.6 인수 기준

- 작업 도구로 verifier에 exec할 수 없다.
- 작업 Pod에서 테스트·검증 설정·결과 저장소를 읽거나 수정할 수 없다.
- 같은 이름의 Pod가 재생성돼도 이전 허가가 적용되지 않는다.
- 임의 Job·서비스 계정·마운트 지정이 거부된다.
- 변조되거나 다른 작업에 속한 산출물·결과가 거부된다.
- 자원 종료·비밀 잔존·정리 실패가 기록되고 추적된다.

## 6. 반영 우선순위와 완료 기준

| 순서 | 반영 항목 | 완료 기준 |

| 1 | 효과 원장·인계 차단 | 응답 유실·워커 종료·지연 명령에서 중복 변경과 잘못된 인계 방지 |
