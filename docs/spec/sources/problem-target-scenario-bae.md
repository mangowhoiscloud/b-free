## 1. 문제정의

> 클라우드 → 온프렘 이전에서 기존 도구는 '옮기기'를 각자 보장하지만, **'옮긴 환경이 원본과 같은 수준으로 안전하고 정확한가(동등성)'는 보장해주지 않음.**

클라우드 매니지드 서비스가 대신 해주던 보안,운영 기능(IAM, KMS, 감사 로그, DB 복제)은 온프렘에서 전혀 다른 형태가 된다. 그래서 환경별 점검 도구로는 원본과 대상을 비교하는 것 자체가 불가능하다.

### 왜 생기나: 클라우드 전환 과정을 리버스 엔지니어링

- 클라우드 전환 방법론([AWS 7Rs](https://docs.aws.amazon.com/prescriptive-guidance/latest/migration-microsoft-workloads-aws/cloud-paths.html))은 Rehost(그대로 이전) → Replatform(약간 수정) → Refactor(새로 설계)로 갈수록 기능을 매니지드 서비스에 맡긴다. → **깊게 클라우드화한 앱일수록 돌아올 때 다시 만들어야 할 것이 많다.**
- 12-Factor(부착된 리소스),Dapr처럼 이식성을 미리 설계한 앱은 이전이 '설정 교체'로 끝나지만, 현실의 앱은 클라우드 SDK를 코드에서 직접 호출한다. → **이전 전에 숨은 의존성 목록이 필요하다.**
- 점진 전환 패턴([Strangler Fig](https://learn.microsoft.com/azure/architecture/patterns/strangler-fig))의 원칙은 "새 시스템을 검증한 뒤에야 옛 시스템을 폐기"다. → **이 순서를 강제하는 장치가 없으면 사고가 난다.**

| 클라우드로 갈 때 맡긴 것 | 돌아올 때 생기는 문제 | 연결되는 문제 |
| --- | --- | --- |
| DB (RDS 등): 백업·복제·페일오버 자동 | 복제,전환,정합성을 직접 책임져야 함 | 데이터 |
| 시크릿·키 (Secrets Manager, KMS) | 암호화 수준 재현 실패 | 보안 |
| IAM 역할,정책 | 권한 매핑 누락 → 과권한 또는 공백 | 보안 |
| 감사 로그,위협 탐지 (CloudTrail, GuardDuty) | 이전 시점에 로그가 끊김 | 보안 |

### 기존 이전 도구가 보장하는 것과 보장 해주지 못하는 것

| 층 | 대표 도구 | 보장하는 것 | 보장하지 않는 것 |
| --- | --- | --- | --- |
| 서버 이동 | [AWS MGN](https://docs.aws.amazon.com/mgn/latest/ug/source-servers.html) | 서버 복제·전환 | AWS로 들어오는 방향 전용 |
| K8s 이동 | [Velero](https://docs.stakater.com/kubestackplus/managed-addons/velero/limitations.html) | K8s 리소스 백업·복원 | 클라우드 간 볼륨 스냅샷 복원 불가, LB 설정 수작업 |
| 데이터 복사 | [AWS DMS](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Target.PostgreSQL.html), [Postgre 논리 복제](https://www.postgresql.org/docs/18/logical-replication-restrictions.html) | 데이터 복사 | 시퀀스(누적된 데이터 행 다음 번호), DDL(데이터 설계 변경) 미복제 |
| 코드 분석 | [VMware CSA](https://learn.microsoft.com/en-us/azure/developer/java/migration/cloud-suitability-analyzer), Konveyor | 코드 패턴 분석, 온프렘→ 클라우드 전환 편가 | 클라우드→ 온프렘 전환 평가 |
| 보안 점검 | [Prowler](https://dev.co/security/open-source/prowler) 등 CSPM | 환경별 CIS,PCI 기준 점검 | 퍼블릭 클라우드 중심(온프렘 공식 지원 X), 원본-대상 비교 X |

→ 결론

① **방향 비대칭**: 클라우드로 '들어가는' 도구는 많지만 '나가는' 도구는 비어 있음

② **동등성 검증 부재**: 각 도구가 자기 영역만 봄

### 근거 (최근 3년)

| 영역 | 사례 | 무슨 일이 있었나 |
| --- | --- | --- |
| 데이터 | [LootLocker (2026.4)](https://lootlocker.com/blog/db-postmortem-data-loss-during-database-migration) | 라이브 마이그레이션 후 일부 데이터가 복제되지 않았는데, 검증 전에 원본 DB를 삭제. 누락 신호가 없었음 |
| 데이터 | [PostgreSQL 공식 문서](https://www.postgresql.org/docs/18/logical-replication-restrictions.html) | 논리 복제는 시퀀스 값,DDL을 복제하지 않음 → 전환 직후 PK 충돌 가능 |
| 보안 | [Tea 앱 (2025.7)](https://www.security.org/identity-theft/breach/tea-app/) | 2024.2 인프라 이전 때 놓친 레거시 Firebase 버킷 노출, 신분증 사진 포함 약 7.2만 장 유출 |

공통점: 각 도구는 제 할 일을 했는데, **검증보다 실행이 먼저 일어난 지점**에서 사고가 났다.

### 해결법: 검증 우선 마이그레이션 파이프라인 (핵심: 원본 대조 게이트)

**설계 원칙**: 결정적 워크플로우(코드)가 흐름을 쥐고, 비결정적 판단(에이전트)은 정해진 지점에서만 한다.

[(참고용) 결정적 워크플로우 × 비결정적 판단 구현안](https://app.notion.com/p/40b8bee9ada4806db38fff11ecc4f16b)

**왜 에이전트에게 실행을 맡기지 않나**: [Replit (2025.7)](https://yourstory.com/ai-story/replit-ai-deletes-production-database)에서 코드 프리즈 중 에이전트가 운영 DB를 삭제하고 허위 보고했다. 사후 조치(개발·운영 DB 분리, 스테이징 의무화)가 설계와 같은 방향

> ⛔ **원본 대조 게이트란?** 컷오버(운영 트래픽을 새 환경으로 넘기는 순간) 직전에, **원본과 이전환경에 같은 질문을 던져 답이 같은지** 비교하는 관문. 하나라도 다르면 전환을 막는다.

| 질문 (예시) | 원본 (AWS) | 대상 (온프렘) | 판정 |
| --- | --- | --- | --- |
| 인증 없이 첨부파일 저장소에 접근되는가? | 거부 | 허용 | ❌ 차단 |
| 메시지 행 수,체크섬이 같은가? | 12,345 / a1b2 | 12,345 / a1b2 | ✅ 통과 |
| 다음 메시지 ID(시퀀스)는? | 12,346 | 1 | ❌ 차단 |

- **스모크 테스트와의 차이**: 헬스체크·DB 연결 확인은 대상 하나만 보고 "떴나"를 본다(기존 도구에도 있음). 원본 대조 게이트는 **원본과 비교**한다 → 기존 도구가 안 하는 부분 = 우리 차별점
- **판정은 LLM이 아니라 규칙이 한다**: 같은 입력이면 항상 같은 결과(일관성)

**파이프라인 흐름** (게이트는 그중 3번)

1. 의존성 인벤토리 (에이전트)
   - 코드,IaC에서 클라우드 의존성을 찾아 3등급으로 분류: 설정만 교체 / 어댑터 추가 / 코드 수정 필요
2. 설정변환 (에이전트, 샌드박스 안에서만)
   - 클라우드에서 쓰던 설정을 온프렘에서 같은 의미로 동작하는 설정으로 변환
     ex ) IAM → K8s RBAC·Vault 정책, KMS → Vault, CloudTrail → 온프렘 감사 로그
3. 원본 대조 게이트 (결정적 규칙)
   - 보안: 원본에서 거부되던 접근이 대상에서도 거부되는지 **실제로 접근을 시도해서** 확인. 기준선은 [전자금융감독규정 시행세칙 별표7](https://shinkim.com/kor/media/newsletter/pdf/3105) 통제 항목(안전한 인증,최소 권한,구간 암호화,로그 수집 등)
   - 데이터: 복제 지연 0, 행 수·체크섬 일치, 시퀀스 ≥ 최대 ID
4. 컷오버
   - 게이트 통과 + 사람 승인 후에 전환. 원본은 대조 결과 리포트가 나올 때까지 롤백용으로 보존

**전 과정 공통 · 에이전트 경계**: 에이전트는 운영 환경 자격증명이 없고, 파괴적 명령은 차단 목록으로 막는다.

## 3. 사용자 시나리오:

**배경**: 금융사 플랫폼팀 엔지니어 A. AWS에서 운영 중인 고객 상담 채팅 서비스에 개인신용정보가 쌓이면서 온프렘 이전이 결정됨. 조건은 두 가지: ① 상담을 멈추지 않을 것 ② 이전 후에도 같은 보안 수준임을 증빙할 것

**구성**: 원본 = AWS (앱 + RDS PostgreSQL + S3 첨부파일 + KMS + IAM) → 대상 = 온프렘 VM 위 K3s 클러스터 (앱 + PostgreSQL + MinIO + Vault)

| 단계 | 무슨 일이 일어나나 | 막힌 것 / 증명된 것 |
| --- | --- | --- |
| ① 이전 시작 | A가 원본(AWS)과 대상(온프렘 K3s)을 플랫폼에 연결. 플랫폼이 RDS·S3·IAM·KMS 설정을 수집 |  |
| ② 의존성 확인 | 에이전트가 코드·설정을 분석해 3등급 목록 작성: DB 주소(설정 교체), S3 SDK(어댑터 추가), KMS 직접 호출(코드 수정) | 어디가 위험한지 이전 전에 드러남 |
| ③ 설정 변환 | 에이전트가 샌드박스 네임스페이스에서 IAM → K8s RBAC·MinIO 정책, KMS → Vault 변환안 작성. 도중에 '정리'를 이유로 기존 버킷 삭제 명령을 시도 | 🛑 도구(코드) 계층에서 삭제 명령 차단 기록 (운영 자격증명 없음) |
| ④ 데이터 동기화 | 논리 복제 시작. 서비스는 여전히 AWS에서 운영 중 (심사위원이 QR로 채팅 중) |  |
| ⑤ 원본 대조 (1차) | 원본·대상에 같은 질문: 첨부 저장소 무인증 접근? 행 수·체크섬? 다음 메시지 ID? | ❌ 대상 저장소가 열려 있음, 시퀀스 1 → 컷오버 차단 |
| ⑥ 수정 | 에이전트가 샌드박스에서 정책 수정안 + 시퀀스 보정 스크립트 제시 → 재대조 | ✅ 모든 항목 일치 |
| ⑦ 승인 | A가 원본 대조 리포트를 확인하고 승인 | 사람이 최종 결정 |
| ⑧ 컷오버 | 쓰기 잠시 정지 → 복제 따라잡기 → 트래픽을 K3s 쪽으로 전환(Argo Rollouts) → 쓰기 재개 |  |
| ⑨ 확인 | 기존 채팅 내역 그대로, 새 메시지도 ID 충돌 없이 저장. AWS는 롤백용으로 보존 | ✅ 데이터 유지 + 서비스 지속 |
