클라우드 출구전략 플랫폼 설계 문서

가동 중인 서비스를 AWS에서 온프레미스로 멈추지 않고 옮기고, 옮긴 환경이 원본과 같은 수준으로 안전하고 정확한지 검증 게이트로 확인한 뒤에만 전환한다.

1개요

금융 서비스가 클라우드를 떠나야 할 때(규제, 비용, 계약 종료, 출구전략 시험), 운영팀이 서비스를 멈추지 않고, 데이터를 한 건도 잃지 않고, 같은 보안 수준을 유지하며 옮길 수 있게 하는 마이그레이션 플랫폼이다. 킥오프 주제(Beyond Lock-In)에 대해 "떠날 수 있다"를 실제 이전과 되돌리기로 보여 준다.

데모 한 줄. 심사위원이 QR로 참여한 금융 상담 채팅을 AWS에서 온프렘으로 옮긴다. 게이트가 열린 첨부파일 저장소를 발견해 전환을 막고, AI가 목적지의 격리된 리허설 환경에서 고친 뒤 재대조를 통과한다. 쓰기를 수 초만 멈추고 컷오버한 다음, 목적지에 장애를 넣어 그사이 쌓인 메시지까지 들고 AWS로 되돌아간다.

전체 구조는 7.1 그림에 있다.

설계 원칙

  1. 에이전트를 믿지 않고 결과를 검증한다. 결정적 워크플로(코드)가 흐름을 쥐고, AI는 정해진 지점에서 정해진 형식의 제안서만 낸다. 실행과 판정은 파이프라인이 한다.
  2. 동등성은 제품 이름이 아니라 시험 결과로 판단한다. "Vault가 있으니 KMS와 같다"가 아니라, 원본에서 거부되던 접근이 대상에서도 실제로 거부되는지 시험한다.
  3. 불명확하면 쓰기를 열지 않는다. 어느 순간에도 업무 쓰기를 받는 DB는 최대 하나다. 상태를 확인할 수 없으면 가용성보다 데이터 안전을 택해 멈춘다(SAFE_HOLD).

2.2핵심 문제

금융사는 클라우드를 언제든 떠날 수 있도록 출구전략을 세우고 시험해야 한다. 그러나 기존 도구는 각자 '옮기기'만 보장할 뿐, 옮긴 환경이 원본과 같은 수준으로 안전하고 정확한지(동등성)는 보장하지 않는다. 그래서 가동 중인 서비스를 멈추지 않고, 데이터를 잃지 않고, 같은 보안 수준으로 옮길 수 있는지는 실제로 옮겨 보기 전까지 알 수 없다.

2.3근거

① 떠날 수 있어야 한다는 요구는 이미 감독 문서에 있다

  • 일본: 금융청 사이버보안 가이드라인 2.6(2024-10)은 중요한 제3자 서비스에 출구전략을 미리 세우고 대체 수단을 정기적으로 시험하라고 권고한다(의무가 아닌 권고 사항). 금융청 디스커션 페이퍼(2023-04)는 클라우드별 인력 비용 때문에 멀티 클라우드가 현재로서는 어렵다는 의견을 소개했다.
  • 한국: 금융보안원 클라우드 이용 가이드는 도입 단계에서 출구전략을 세우고, 이용 종료 시 그에 따라 데이터를 이전 · 파기하도록 안내한다. 전자금융감독규정 시행세칙 별표7은 안전한 인증, 최소 권한, 구간 암호화, 로그 수집 같은 통제 항목을 둔다.
  • EU: DORA 28조 8항(2025-01 적용)은 중요 기능을 받치는 ICT 서비스에 출구전략을 요구하고, 문서화와 충분한 시험을 요구한다.

② 클라우드로 깊게 들어갈수록 돌아올 때 다시 만들 것이 많다

클라우드 전환 방법론(AWS 7Rs)은 Rehost → Replatform → Refactor로 갈수록 기능을 매니지드 서비스에 맡긴다. 거꾸로 돌아올 때는 그만큼을 다시 만들어야 하고, 앱 코드가 클라우드 SDK를 직접 부르면 숨은 의존성이 된다.

클라우드에 맡겼던 것온프렘으로 돌아올 때 생기는 문제연결되는 중점
DB 운영(백업 · 복제 · 페일오버)복제 · 전환 · 정합성을 직접 책임져야 함② 무결성
시크릿 · 키 (Secrets Manager, KMS)암호화와 키 접근 분리 수준을 재현하지 못함① 보안
IAM 역할 · 자원 정책권한 매핑 누락 → 과권한 또는 공백① 보안
객체 저장소 정책 (S3)버킷 공개 여부 · 권한이 바뀐 채 열림① 보안
감사 로그 (CloudTrail)이전 시점에 로그가 끊김① 보안

③ 기존 도구는 자기 층만 보고, 방향도 비대칭이다

결론은 두 가지다. 클라우드로 들어가는 도구는 많지만 나가는 도구는 비어 있고, 각 도구가 자기 층만 보기 때문에 원본과 대상의 동등성을 검증하는 장치가 없다.

3타겟 사용자

금융사(은행 · 증권 · 결제)에서 K8s · PostgreSQL 기반 서비스의 출구전략 시험과 이전을 맡는 플랫폼 · 인프라 운영팀

왜 금융인가: 우리가 고른 중점(보안 유지, 무결성)이 가장 무겁게 요구되고, 출구전략과 그 시험이 감독 문서에 적혀 있기 때문이다. 발표 서사는 일본 금융사를 기준으로 하고, 한국 금융사도 같은 요구를 받는다는 점을 보조로 보인다.

이 팀이 지켜야 하는 것이유
서비스가 멈추면 안 된다송금 · 결제 · 상담이 끊기면 바로 고객 피해와 민원이 된다
데이터가 한 건도 어긋나면 안 된다거래 · 상담 기록이 틀리면 금전 사고와 분쟁이 된다
옮긴 뒤 같은 보안 수준임을 증명해야 한다감사 대응, 정보보호위원회 · 감독당국 보고에 근거 자료가 필요하다
출구전략이 실제로 작동해야 한다문서로만 있는 계획은 막상 필요할 때 검증돼 있지 않다
AI가 만든 변경은 사람이 승인해야 한다AI 지침(AI 사업자 가이드라인 1.2판 등)은 폐쇄 환경 검증, 최소 권한, 사람의 개입과 정지를 다룬다
함께 쓰는 사람하는 일
주 사용자: 플랫폼 · 인프라 운영팀환경 등록, 이전 실행, 장애 대응
승인자: 보안 · 감사 책임자통제 비교 결과와 AI 변경안을 보고 승인, 감사 자료 작성
협업: 앱 개발팀의존성과 허용 가능한 중단 조건을 알려 주고, AI가 만든 코드 변경을 검토

지금은 점검 시간을 공지하고 멈춘 뒤 옮기거나 출구전략을 문서로만 두고, 데이터 검증 · 통제 비교 · 의존성 검사가 도구마다 흩어져 있다고 가정한다(운영팀 인터뷰 미확인). 금융사에 설치형을 납품하는 SaaS 기업과 공공 시스템은 확장 대상이다.

4목표와 비목표

목표

  • 가동 중인 채팅 서비스를 AWS → 온프렘으로 쓰기 정지 수 초 안에 이전
  • 실패 · 유실 · 중복 0건을 요청 ID 대조로 증명
  • 컷오버 전 원본 대조 게이트로 보안 · 데이터 동등성 판정, 다르면 차단
  • 6개 통제의 이전 전후 비교표
  • AI는 격리된 리허설에서만 의존성 분석 · 번역 · 수정, 별도 검증과 사람 승인 뒤에만 반영
  • 목적지 장애 시 그사이 쓴 데이터까지 들고 되돌리기
  • 모든 단계 · 판정 · 차단 · 승인의 수정 불가 기록
  • 설계는 목적지 무관(어느 RKE2 환경이든), 데모는 AWS → 온프렘

비목표 (이번 범위 밖)

  • RDS 같은 관리형 DB를 출발지로 쓰는 이전 (P2, 가져오기 경로)
  • AWS → GCP 이전, 본부의 GCP 이전 (P2 확장)
  • 여러 앱 동시 이전, 웨이브 계획
  • 호환되지 않는 스키마 변경, DB 종류 변환
  • failback 뒤 재이전
  • Edge(Cloudflare)의 독립 대체 진입점
  • 클러스터 안 버전 교체 전략(Argo Rollouts) (P2)
  • AI 추론 서비스 · ETL 파이프라인 이전 (P2~P3)

5.1기능 요구사항

ID요구사항우선
FR-1운영팀이 출발지(AWS)와 목적지를 등록하면, 플랫폼은 클러스터 · DB · S3 정책 · IAM · KMS · Secrets Manager 설정을 읽기 전용으로 수집한다.P0
FR-2코드와 IaC에서 클라우드 의존성을 찾아 3등급(설정 교체 / 어댑터 추가 / 코드 수정)으로 분류한다. 탐지는 정적 분석, 애매한 분류만 AI가 한다.P0
FR-3목적지는 Terraform과 공통 cloud-init으로 같은 기준(RKE2 CIS, CNPG, OpenBao, SeaweedFS)으로 세운다.P0
FR-4AI는 IAM · S3 정책 · Secrets Manager · KMS를 목적지의 RBAC · SeaweedFS 정책 · OpenBao로 옮기는 번역안과 코드 수정안을 정해진 스키마의 제안서로만 낸다.P0
FR-5제안서는 목적지 클러스터의 격리된 리허설 네임스페이스에서만 적용 · 시험하고, 플랫폼이 보관한 비공개 테스트를 별도 검증 Job으로 돌려 채점한다. 실패하면 최대 3회 재시도 후 사람에게 넘긴다.P0
FR-6컷오버 전 원본 대조 게이트가 원본과 대상에 같은 보안 질문과 데이터 경로 준비 질문(스키마, 복제 지연, 시퀀스 보정)을 던져 결정적 규칙으로 판정한다. 하나라도 다르거나 UNKNOWN이면 차단한다.P0
FR-7게이트 통과와 사람 승인 없이는 컷오버할 수 없다. 승인은 대상 값(계획, diff, 이미지 digest, 만료)에 묶인다.P0

FR-9컷오버는 논리 복제 + PgBouncer PAUSE/RESUME + 펜싱 + barrier로 하고, 쓰기 정지 시간을 단계별로 기록한다. 업무 쓰기를 받는 DB는 어느 순간에도 최대 하나다.P0

6사용자 시나리오

공통 배경. 금융사 플랫폼팀 엔지니어 A. AWS에서 운영 중인 고객 상담 채팅(사람 간 실시간 채팅)에 개인신용정보가 쌓이면서 온프렘 이전이 결정됐다. 조건은 두 가지다. 상담을 멈추지 않을 것, 이전 후에도 같은 보안 수준임을 증빙할 것.

구성. 출발지 = AWS EKS(채팅 앱 + CNPG Postgres) + S3 첨부파일 + Secrets Manager + KMS + IAM. 목적지 = 온프렘 Ubuntu VM 위 RKE2(채팅 앱 + CNPG + SeaweedFS + OpenBao).

시나리오는 실제 이전이 일어나는 시간 순서다. 예외 번호는 기본 흐름의 단계 번호를 따른다(3a = 3단계의 예외).

S1목적지를 세우고 원본과 비교한다 중점 ①

"옮기기 전에, 목적지가 원본만큼 안전한지와 무엇이 빠져 있는지 먼저 알고 싶다."

주 사용자플랫폼 · 인프라 운영팀 (승인: 보안 · 감사 책임자)
계기출구전략 점검이나 이전 계획에서 대체 환경이 필요하다
시작 조건출발지에서 채팅이 가동 중이다. 목적지에는 빈 Ubuntu VM을 만들 수 있다
종료 조건목적지에 같은 기준의 클러스터가 서고, 의존성 목록과 통제 비교표가 나온다. 게이트 판정이 기록된다
실패해도 지킬 것출발지 운영 환경은 바뀌지 않는다(읽기 전용 수집). 구축이 실패하면 목적지 자원을 지우고 다시 만든다

기본 흐름

  1. A가 출발지(AWS 계정, EKS)와 목적지(온프렘 VM)를 플랫폼에 등록한다.
  2. 플랫폼이 읽기 전용 역할로 출발지 설정을 수집한다: S3 버킷 정책, IAM 역할, KMS 키 정책, Secrets Manager 항목, CNPG 구성.
  3. 플랫폼이 코드와 IaC에서 클라우드 의존성을 정적으로 찾고, AI가 3등급으로 분류한다. 예: DB 주소 = 설정 교체, S3 SDK = 주소 교체(S3 호환), Secrets Manager · KMS 직접 호출 = 코드 수정.
  4. 플랫폼이 Terraform과 공통 cloud-init으로 목적지에 RKE2(CIS), CNPG, OpenBao + ESO, SeaweedFS를 세운다. 데모에서는 사전 구축하고 실행 기록을 보인다.
  5. 6개 통제를 양쪽에서 같은 방법으로 시험해 통제 ID별 비교표를 만든다.
  6. 원본 대조 게이트 1차를 돌린다. 데모에서는 목적지 첨부 저장소가 인증 없이 열려 있어 BLOCK이 나오고, 이전 후보 등록이 보류된다 → S2.

예외 흐름

  • 4a. RKE2 CIS 프로필이 조건 미충족으로 시작을 거부한다 → 공통 cloud-init의 조건(sysctl, etcd 사용자)을 고치고 재설치한다.
  • 5a. 시험 결과가 UNKNOWN이다 → PASS로 보지 않고 차단한다.
  • 5b. 목적지에서 대체할 수 없는 통제가 있다 → 승인자가 예외를 승인하면 "예외 승인"으로 따로 표시하고 동등 판정에서 뺀다.

인수 조건

  • Given 빈 VM만 있는 목적지, When 구축을 실행하면, Then RKE2가 CIS 프로필로 뜨고 실행 기록이 남는다.
  • Given 두 환경, When 통제 시험을 돌리면, Then 6개 통제의 PASS / FAIL / UNKNOWN이 통제 ID별로 나온다.
  • Given 예외 승인 없는 FAIL이나 UNKNOWN, When 이전 후보 등록을 시도하면, Then 등록이 막힌다.

S2AI가 격리된 리허설에서 차이를 메운다 중점 ③

"빠진 설정과 클라우드 전용 코드는 AI에게 맡기고 싶다. 그래도 AI가 운영 환경과 비밀에는 닿지 못하게 하고 싶다."

주 사용자운영팀(승인자), 앱 개발팀(검토), AI 에이전트(보조)
계기S1에서 FAIL 통제와 "코드 수정" 등급 의존성이 나왔다
시작 조건원본 저장소는 읽기 전용, 쓰기는 리허설 네임스페이스 안 작업 복사본에만. 에이전트는 클러스터 자격증명이 없고, 모델 키는 플랫폼에만 있다. 목적지는 아직 컷오버 전이다
종료 조건검증을 통과하고 사람이 승인한 변경만, 승인된 이미지 digest로 목적지에 배포된다. 게이트 재대조가 통과하고 리허설 네임스페이스는 삭제된다
실패해도 지킬 것리허설 네임스페이스에서 네임스페이스 밖 · 메타데이터 · 임의 외부로 가는 접속은 모두 거부되고 기록된다

기본 흐름

  1. 플랫폼이 차이(FAIL 통제, 코드 수정 등급 의존성)를 작업(task)으로 등록한다.
  2. 작업마다 목적지 클러스터에 새 리허설 네임스페이스를 만든다. 앱 복사본, 합성 데이터 DB, 목적지 프로필(시험용 OpenBao 경로 · SeaweedFS 버킷)만 넣는다.
  3. 에이전트(본부의 워커)가 제안서를 낸다. 예: Secrets Manager 직접 호출 → OpenBao · ESO 주입으로 코드 수정, SeaweedFS 버킷 정책 작성.
  4. 리허설 네임스페이스에서 적용하고 시험한다. 명령은 플랫폼의 도구 계층이 대신 실행한다. 실패하면 원인을 분석해 다시 시도한다(최대 3회).
  5. 플랫폼이 비공개 테스트를 별도 검증 Job으로 돌려 채점한다. 통과하면 원본 대조 게이트를 다시 돌려 PASS를 확인한다.
  6. 앱 개발팀이 변경을 검토하고, 운영팀이 승인한다. 승인은 diff와 이미지 digest에 묶인다.
  7. 같은 digest의 이미지만 목적지에 배포된다.

예외 흐름

  • 4a. 3회 시도해도 실패한다 → AI는 멈추고, 시도한 수정과 남은 오류를 정리해 사람에게 넘긴다.
  • 4b. 네임스페이스 밖 · 메타데이터 · 외부 접속이나 파괴적 명령(예: 버킷 삭제)을 시도한다 → 도구 계층과 네트워크에서 차단하고 기록한다. 데모 장면.
  • 5a. 검증 판정이 실패 · 누락 · timeout이다 → 변경안을 BLOCK한다.
  • 6a. 사람이 거절한다 → 반영하지 않고 거절 사유를 기록한다.
  • 7a. 승인 뒤 diff나 digest가 바뀌었다 → 배포를 막고 5단계부터 다시 검증한다.

인수 조건

  • Given 리허설 네임스페이스에서 작업 중인 AI, When 운영 환경이나 외부로 접속하려 하면, Then 막히고 시도가 기록된다.
  • Given 검증을 통과한 변경안, When 아무도 승인하지 않으면, Then 목적지에 반영되지 않는다.
  • Given 승인된 변경안, When 배포 이미지 digest가 승인 값과 다르면, Then 배포가 거부된다.
  • Given 끝난 리허설, When 네임스페이스와 비밀 잔존을 검사하면, Then 네임스페이스가 남아 있지 않고 모델 키와 운영 자격증명이 발견되지 않는다.
  • Given 컷오버가 확정된 목적지, When 리허설을 시작하려 하면, Then 상태 머신이 거부한다.

S3멈추지 않고 옮긴다 중점 ② ①

"상담이 오가는 중에 옮기고, 기록이 한 건도 어긋나지 않았다는 증거를 받고 싶다."

주 사용자운영팀 (통제 비교 승인: 보안 · 감사 책임자)
계기출구전략 시험, 규제, 비용, 계약 변경
시작 조건S1 · S2 완료(게이트 PASS, 승인). 양쪽 스키마가 같고, 출발지 CNPG → 목적지 CNPG 논리 복제가 Tailscale 경로로 따라오고 있다
종료 조건목적지가 업무 쓰기를 받는 유일한 DB가 되고, 출발지는 역방향 복제로 따라오며 대기한다. 무결성 영수증과 통제 전후 비교가 남는다
실패해도 지킬 것업무 쓰기를 받는 DB는 어느 순간에도 최대 하나(전환 중에는 0개). 상태가 불명확하면 쓰기를 새로 열지 않는다

기본 흐름

  1. 부하(쓰기 50 req/s)가 걸린 상태에서 Edge 가중치를 10% → 50% → 100%로 올려 앱 트래픽을 목적지로 옮긴다. 이때 쓰기는 여전히 출발지 DB가 받는다(목적지 앱은 목적지 PgBouncer를 거쳐 Tailscale로 출발지 DB에 쓴다).
  2. 운영팀이 복제 지연과 쓰기 정지 예산을 확인하고 컷오버를 승인한다.
  3. Executor가 새 쓰기를 막고 PgBouncer를 PAUSE한 뒤, 출발지를 펜싱하고 barrier(표식 행)가 목적지에 도착했는지 확인한다.
  4. 양쪽 쓰기가 막힌 상태에서 행 수 · PK 해시 · 내용 해시를 비교한다. 일치하면 시퀀스를 올리고, 정방향 복제를 멈추고, 역방향 복제를 켠다.
  5. 전환 확정을 기록한 뒤 목적지 쓰기를 열고 PgBouncer 대상을 바꿔 RESUME한다. 열린 WebSocket은 서버가 닫고(코드 1012) 클라이언트가 재접속한다.
  6. 쓰기 정지 시간과 무결성 영수증을 저장하고, 6개 통제를 다시 시험해 전후 비교표를 남긴다.

예외 흐름

  • 1a. 오류율이나 p95가 기준을 넘는다 → 가중치를 0으로 돌린다.
  • 3a. 펜싱이나 barrier 확인이 정한 시간 안에 끝나지 않는다 → 전환 확정 전이므로 취소하고 출발지 쓰기를 다시 연다(ABORT_PRE_WRITE).
  • 4a. 비교가 맞지 않는다 → 3a와 같이 취소하고 출발지를 그대로 쓴다.
  • 6a. 통제 재시험이 실패한다 → 이전 완료로 판정하지 않고, 원인을 고치거나 S4로 되돌린다.
  • 공통. 전환 확정 뒤 원격 상태를 확인할 수 없다 → 어느 쪽도 쓰기를 자동으로 열지 않고 SAFE_HOLD, 사람에게 넘긴다.

인수 조건

  • Given 쓰기 50 req/s 부하, When 컷오버하면, Then 실패 · 유실 · 중복과 쓰기 정지 시간이 기록되고 목표는 0건 · 5초 이하다.
  • Given 양쪽 쓰기가 막힌 상태, When 두 DB를 비교하면, Then 행 수 · PK · 내용 해시가 같고 결과는 목적지 쓰기 전에 저장된다.
  • Given 이전 전 통제 결과, When 이전 뒤 같은 방법으로 시험하면, Then 예외 승인 외 FAIL · UNKNOWN이 0개다.
  • Given 심사위원이 쓴 채팅 기록, When 컷오버 뒤 새 메시지를 보내면, Then 기존 기록이 그대로 있고 새 메시지 ID가 충돌하지 않는다.

S4문제가 생기면 데이터째 되돌린다 중점 ②

"옮긴 직후 문제가 생기면, 그사이 쌓인 상담 기록까지 들고 원래 환경으로 돌아가고 싶다."

주 사용자운영팀
계기전환 직후 목적지 오류율이 오르거나 통제 재시험이 실패한다
시작 조건S3 완료. 목적지가 주본이고, 출발지는 역방향 복제로 따라오고 있다
종료 조건출발지가 다시 주본이 되고, 전환 뒤 목적지에 쌓인 메시지도 출발지에 모두 있다
실패해도 지킬 것되돌리는 동안 어느 쪽에서도 기록이 사라지지 않는다. AWS–온프렘 경로가 끊긴 동안에는 되돌리기를 하지 않는다

기본 흐름

  1. 목적지 앱에 장애를 넣는다(DB는 생존). 오류율이 기준을 넘어 알림이 간다.
  2. 운영팀이 되돌리기를 결정하고 승인한다.
  3. 목적지 업무 쓰기를 막고, 최종 barrier가 출발지에 도착했는지 확인한 뒤 비교한다.
  4. 출발지 쓰기를 열고 Edge 가중치를 출발지로 돌린다.
  5. 승인자, 시작 · 종료 시각, 복구 시간, 무결성 영수증을 기록한다.

예외 흐름

  • 3a. 출발지가 따라잡지 못했거나 확인할 수 없다 → 쓰기를 열지 않고 SAFE_HOLD, 운영팀이 판단한다.
  • 4a. 되돌린 뒤에도 에러가 계속된다 → 이전과 무관한 장애로 보고 일반 장애 대응으로 넘긴다.

인수 조건

  • Given 전환 뒤 새 메시지가 쌓인 상태, When 되돌리기를 실행하면, Then 그 메시지가 모두 출발지에 있고 손실은 0건이다.
  • Given 되돌리기 완료, When 기록을 확인하면, Then 승인자, 시각, 복구 시간, 영수증이 남아 있다.

7.2배치

플랫폼(본부)은 출발지 앱과 같은 AWS 계정에 두되 VPC를 나눈다. 평상시 사용자 요청과 DB 복제는 플랫폼을 거치지 않는다. 플랫폼은 환경을 세우고, 검증하고, 옮기는 일만 지휘한다.

8상세 설계

8.1결정 · 비결정 기준

"과정이 정해져 있는가"와 "결과가 항상 같아야 하는가"로 나누면 네 칸이 나온다. AI가 실행(컷오버 · 롤백)에 들어가는 칸은 없다.

결과가 항상 같아야 함결과가 달라도 됨
과정이 정해짐코드만: 게이트 판정, 통제 시험, 컷오버, 롤백AI 작성 + 사람 확인: 정해진 데이터로 리포트 · 승인 요약 작성
과정이 정해지지 않음AI가 시도, 코드가 합격선 고정: S2 수정 루프 (검증 통과해야 끝)AI 제안 + 사람 판단: 애매한 의존성 분류, 장애 원인 추정

에이전트는 제안서만 내고, 실행과 판정은 파이프라인이 한다. 단계별 역할은 7.1 그림의 번호 단계와 같다.

8.2상태 머신

이전 작업 하나가 지금 어느 단계에 있는지 기록하고, 다음 단계로 넘어갈 조건을 코드에 고정한다. 에이전트가 단계를 건너뛸 수 없고, 상태와 전이가 그대로 콘솔 진행 표시와 감사 기록이 된다. 워크플로 엔진 없이 직접 구현한다. 상태는 플랫폼 DB에 저장하고, 재기동하면 마지막 상태와 실제 원격 효과를 다시 읽고 이어 간다.

8.3에이전트

  • SDK: Claude Agent SDK. 예선 피드백("로컬 스킬보다 클라우드 워커에서 도는 AI 네이티브 에이전트")을 반영해 플랫폼의 워커 프로세스로 실행한다. 모델 키는 플랫폼에만 있다.
  • 할 일: 의존성 분류, 번역 · 수정 제안서, 실패 원인 추정, 승인자용 요약, 사후 리포트 초안.
  • 못 하는 일: 실행, merge, 배포 동기화, 운영 자격증명 사용. 도구 목록에 아예 없다.
  • 교차 검토(P1): 다른 모델에 변경안 검토를 1회 맡겨 의견을 승인 화면에 붙인다.
  • CI 에이전트: 별도로 두지 않는다. 실패 분석 → 수정 → 재시도는 S2 루프가 같은 일을 한다.

8.4리허설 네임스페이스

에이전트가 만든 변경은 목적지 클러스터의 격리된 리허설 네임스페이스에서만 적용하고 시험한다. 실제 목적지와 같은 RKE2 · OpenBao · SeaweedFS에서 돌려 보므로, 흉내 낸 환경에서는 놓치는 차이를 컷오버 전에 잡는다. Harbor 도입 문서의 방안 1(런타임은 직접 띄운 네임스페이스, Harbor는 평가 전용)을 따른다.

흐름

  1. 상태 머신이 REHEARSE에 들어가면 리허설 러너가 rehearsal-<plan>-<n> 네임스페이스를 템플릿으로 만든다. 컷오버가 확정된 뒤에는 만들지 않는다.
  2. 앱 이미지 복사본, 합성 데이터 DB, 목적지 프로필(시험용 OpenBao 경로 · SeaweedFS 버킷)만 넣는다.
  3. 생성 직후 격리 시험을 자동으로 돌린다. 하나라도 실패하면 BLOCK한다.
  4. 에이전트는 자격증명 없이 rehearsal.exec 도구만 부른다. 도구 계층이 차단 목록을 확인하고, 그 네임스페이스로만 권한이 묶인 서비스 계정으로 대신 실행한다.
  5. 플랫폼이 보관한 비공개 테스트를 별도 검증 Job으로 실행해 채점한다. 에이전트는 테스트를 볼 수도 고칠 수도 없다.
  6. 결과, 도구 호출, 차단 기록을 감사 로그에 남기고 네임스페이스를 지운다.

8.6데이터 이전과 Cutover Executor

데이터 이전 방식은 10/31 팀 합의를 그대로 따른다: PostgreSQL 논리 복제로 초기 데이터를 복사하고 변경분을 따라간 뒤, PgBouncer(transaction 풀링)를 잠깐 PAUSE하고 대상을 바꿔 RESUME한다. Executor는 이 짧은 쓰기 정지 구간을 정해진 순서로 실행하는 프로그램이며, 팀이 직접 만드는 핵심 부품이다.

  • 복제 전 준비: 논리 복제는 DDL을 옮기지 않으므로, 구독을 시작하기 전에 목적지에 같은 스키마를 마이그레이션 Job으로 만든다.
  • 전환 전 쓰기 경로: 트래픽 전환(S3 1단계) 동안 목적지 앱은 목적지 PgBouncer를 거쳐 Tailscale로 출발지 DB에 쓴다. 두 PgBouncer가 모두 출발지 DB를 가리키다가, 컷오버 7단계에서 함께 목적지 DB로 바뀐다. 이 구간은 클라우드를 넘는 쓰기라 p95가 늘어나므로, 가중치 단계의 판정 기준은 실측 지연(T8)으로 정한다.

컷오버 순서

  1. 복제 지연이 기준 이하인지 확인하고, lease와 단조 증가 epoch를 얻는다. 첫 쓰기 제한 직전에 타이머를 켠다.
  2. 모든 진입점에서 새 업무 쓰기를 막고, 적용됐는지 확인한다.
  3. 두 PgBouncer에 PAUSE를 보낸다. PAUSE는 진행 중인 트랜잭션을 기다리므로 직전에 긴 트랜잭션이 없는지 확인하고, deadline을 넘기면 쓰기 전 실패로 처리한다.
  4. 출발지를 펜싱한다: 앱 쓰기 역할의 새 로그인을 막고, 기존 세션이 끝났는지와 우회 쓰기(worker, CronJob, 직접 연결)가 없는지 확인한 뒤, 업무 쓰기가 실제로 거부되는지 시험한다.
  5. 제어 역할로 barrier를 commit하고 목적지 도착을 확인한다. 최종 비교(행 수 · PK 해시 · 내용 해시)를 하고 시퀀스를 올린다.
  6. 정방향 apply가 멈춘 것을 확인하고 역방향 구독을 켠다. 전환 확정을 기록한다.
  7. 목적지 쓰기 역할을 켜고, 두 PgBouncer의 대상을 바꿔 RELOAD한 뒤 RESUME한다. 출발지의 열린 WebSocket을 닫는다(1012).
  8. 실제 pool 경로로 목적지 접속을 확인하고 진입점 쓰기 제한을 푼다. 마지막 경로의 업무 쓰기 응답(ACK)에서 타이머를 끈다. 이 구간이 쓰기 정지 시간이다.

8.7트래픽 전환

Argo Rollouts는 한 클러스터 안에서 버전을 바꾸는 도구라 클러스터를 넘는 전환을 못 한다. 환경 간 전환은 두 클러스터 바깥, 사용자 앞단에서 한다.

  • Cloudflare LB에 pool 두 개(출발지 · 목적지)를 두고, 각 클러스터는 Tunnel로 바깥 방향 연결만 연다. 온프렘이 공유기 뒤에 있어도 된다.
  • 가중치를 10% → 50% → 100%로 올리며 단계마다 오류율 · p95를 본다. 분배는 요청마다 확률적이므로 실제 비율은 관측값으로 보고한다. 기준을 넘으면 0으로 되돌린다.
  • WebSocket: 가중치 변경은 새 연결에만 적용된다. 컷오버 때 서버가 열린 연결을 코드 1012로 닫고, 클라이언트가 마지막 메시지 ID로 재접속한다.
  • 멱등 키: 모든 메시지 쓰기에 고유 키를 붙여, 쓰기 정지 중 재시도가 유실이나 중복을 만들지 않게 한다.
  • 비용과 의존: Cloudflare LB는 유료(월 약 $5, 무료 플랜 없음)다. Cloudflare는 잔존 의존성으로 의존성 지도에 표시하고, 비상 경로는 DNS 전환으로 둔다.

리허설 네임스페이스컷오버 전 목적지 클러스터에 작업마다 만들고 지우는 격리 공간. 에이전트의 제안서를 적용 · 시험한다
검증 Job플랫폼이 보관한 비공개 테스트로 리허설 결과를 채점하는 별도 실행. 에이전트는 테스트를 볼 수 없다
컷오버업무 쓰기를 받는 DB를 출발지에서 목적지로 바꾸는 순간
쓰기 정지 시간첫 쓰기 제한 직전부터 마지막 경로의 업무 쓰기 응답까지
펜싱 · barrier · epoch출발지 쓰기를 확실히 막는 일 · 복제 도착을 확인하는 표식 행 · 오래된 명령을 거부하기 위한 단조 증가 번호
ABORT_PRE_WRITE목적지에 쓰기 전 실패라 출발지에서 그대로 재개하는 결과
