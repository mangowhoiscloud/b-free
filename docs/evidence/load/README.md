# 부하 측정 (T18, NFR-1 · NFR-2, 스펙 §5.3)

스펙 §5.3 제안값은 쓰기 50 · 읽기 150 req/s입니다(11/2–11/5 실측으로 확정). 여기 기록은 컷오버 없이 잰 것입니다. 부하를 건 컷오버 5회는 사람 승인이 필요해 아직 돌리지 않았습니다(아래 "컷오버 5회").

도구: `tools/loadgen` 앱 방식(쓰기 `POST /api/rooms/<방>/messages`, 읽기 WebSocket 이력). 방법과 출력 형식은 [tools/loadgen/README.md](../../../tools/loadgen/README.md)에 있습니다. 데모 앱에는 HTTP로 메시지를 읽는 API가 없어서, 읽기 하나는 WebSocket 접속 하나입니다.

## 컷오버 5회(NFR-1)

사람 승인이 필요해 돌리지 않았습니다. 준비만 했습니다.

- `deploy/cloud/load_cutover.sh <plan-id> [label]`: 프런트(LB)에 부하를 걸고, 콘솔에서 사람이 시작한 그 계획의 SHIFT · CUTOVER · FAILBACK 실행을 기다려 기록합니다. 승인을 만들거나 실행을 시작하지 않습니다. 실행 기록의 승인 ID를 `run.json`에 남깁니다(`APPROVAL_ID`를 주면 다른 승인을 쓴 실행을 표시).
- 5회가 끝나면 `python -m bravo_loadgen.cutover_stats docs/evidence/load/*-cutover*/run.json`이 쓰기 정지 원측정 · 중앙값 · 최댓값과 NFR-2 합계를 냅니다. DONE이 아닌 실행도 목록에 남깁니다.
- 노드 1대 · WebSocket 읽기 측정대로라면 50 + 150으로는 컷오버 전에 출발지가 먼저 무너졌습니다. 노드 2대 · HTTP 읽기에서는 출발지가 버팁니다(맨 위). 다만 커밋 `9253b8b`부터 Executor가 SHIFT 판정용으로 프런트에 초당 60건을 따로 씁니다. 사용자 부하와 합치면 출발지 쓰기만 초당 약 110건이고, SHIFT 50%면 목적지 경로에 초당 약 55건이 갑니다(위 추정 상한 약 16건). 어떤 비율로 5회를 돌릴지 정해야 합니다.
